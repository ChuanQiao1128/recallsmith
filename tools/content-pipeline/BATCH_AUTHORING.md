# Frozen batch authoring (`batch-v1`)

`batch_author.py` only transports through the reviewed `author.invoke(..., stage, attempt=1, ...)`. It does not run another model provider, synthesize human review, or create a full-RAG gate. Generation and independent review are separate fresh, ephemeral subscription workbench requests. Each output still has an individual concept ID, five claim groups, bilingual checks, and verdict. The shared wrapper is exactly `{"cards":[...]}` with the requested 1–5 objects in input UID order.

## Inputs and commands

Prepare the complete 337-goal catalogue and all `authoring/<uid>/packet.json` with the existing pipeline first. Corpus root is the directory containing `corpus/manifest.json`. The config has exactly four properties:

- `starters`: `awsb-intro-ec2-instance`, `awsb-intro-s3-object-bucket`, `awsb-rds-managed-vs-ec2`, `awsb-intro-iam-permissions`, `awsb-iam-role-not-keys` (in that order).
- `domainCanary`: `cloud=awsb-sig-least-ops`, `networking=awsb-vpc-gateway-endpoint`, `messaging=awsb-in-sqs-visibility-timeout`, `operations=awsb-f-cloudwatch`.
- `edgeCanary`: `rdsStandby=awsb-rds-multi-az-instance-standby`, `rdsReadReplica=awsb-rds-multi-az-vs-replica`, `s3Acceleration=awsb-s3-transfer-acceleration`.
- `legacyUids`: the exact 334 `cards[].stableUid` values from `curriculum/existing-cards.json`.

All twelve canaries must actually exist; no replacement UID is inferred. The config and old-card manifest hash become part of one immutable global plan. The catalogue curriculum hash, corpus version, each full goal hash, packet hash, canonical packet object hash and original packet file hash are also frozen. Model input is a deterministic projection of the complete goal and each packet's own `{evidenceId,url,text}`; full originals and offsets remain available to `author.validate_packet` and `author.validate_card`.

```
python batch_author.py --root CONTROL --corpus-root CORPUS_ROOT plan --config CONFIG.json
python batch_author.py --root CONTROL --corpus-root CORPUS_ROOT run --dotnet DOTNET --workbench-review REVIEW.json --rag-gate CONTROL/evaluation/full-rag-gate.json --limit 12
python batch_author.py --root CONTROL --corpus-root CORPUS_ROOT run --dotnet DOTNET --workbench-review REVIEW.json --rag-gate CONTROL/evaluation/full-rag-gate.json
python batch_author.py --root CONTROL --corpus-root CORPUS_ROOT status
```

Planning makes no model requests. It greedily freezes batches of at most five before execution, with 6,000 characters per card reserved under the workbench's 60,000-character prompt bound. Starter/domain/edge groups remain separate, so the first twelve stay the canary set even if a group must split. `--limit` permits only `12`; removing it resumes the exact same global map and known results. No post-execution regrouping occurs. Every actual review/repair prompt is checked again before transport; an unusually verbose candidate/review can exceed the reserve and stop execution without submitting a request.

`run` requires the independently reviewed workbench and the real parent-produced `aws-basics-rag-gate-v1` PASS. It checks current curriculum/corpus bindings, reference hash, all three report file hashes, 80 reference PASSes, actual 40 holdout retrieval rows, eight themes, 32 positives/eight negatives, readiness decision IDs and counts. Retrieval uses the canonical `evaluation/results/holdout.json`; each row’s Recall/MRR is recomputed with the existing scorer against canonical reference groups and its actual hashed packet, before aggregate metrics are accepted. Recall ≥.9, MRR ≥.75, every theme recall ≥.75, all eight negatives refused, ≤1 false refusal, zero accepted wrong deployments and zero unsupported acceptances are required. The read-only `readiness.verify_decisions` verifier reopens original reader/judge workbench results, receipts, schemas, invocation metadata, completion events and stderr, rebuilding opaque IDs, per-query source-bound retrieval packets and exact reader/judge prompts and rubric before accepting their reported decisions. Report paths and matching summaries alone never authorize dispatch. Both acceptance flags are typed per-decision booleans derived from the actual independent judge verdict; contradictory flags or zero summaries cannot hide an unsupported ready answer. The selected reference review must match the root controller’s `run.json` A3 pin and the exact canonical `evaluation/references.json` bytes/80 IDs. Its authority is the supervisor-observed native independent agent review; this is not represented as a CLI execution or human labeling. The readiness schema is `aws-basics-evidence-readiness-v1`; its metrics contain the five readiness counts, while the full gate additionally carries retrieval metrics.

## Frozen dev adoption and the single holdout observation

For this release, `evaluate.py --split dev` rejects live retrieval. Adopt the existing final bounded dev observation explicitly; do not rerun or tune it. The supervisor must first independently verify and pin `run.json.nodes.A3-dev-selection` with `status=verified`, `sourcePath=evidence/retrieval-final-bounded-repair/final-dev`, and the exact `manifestHash`, `resultsHash`, `frozenSelectionHash`, `frozenPlanHash`, `devReferencesHash`, canonical `referenceHash`, current `retrieverSourceHash`, and current `evaluatorSourceHash`. This node is supervisor-owned; a report's own PASS or recomputed hash is insufficient authority. The active `corpus/retrieval-profile.json` must already equal the independently reviewed winning v3 profile. `A3-reference-review` separately pins the actual observed native reviewer identity, report path/hash, reference hash and provenance; it is not tied to a historical agent name.

```
PYTHON tools/content-pipeline/evaluate.py --root CONTROL --corpus-root CORPUS_ROOT --adopt-frozen-dev
PYTHON tools/content-pipeline/evaluate.py --root CONTROL --corpus-root CORPUS_ROOT --references CONTROL/evaluation/references.json --reference-review PINNED_REFERENCE_REPORT --model-cache ORIGINAL_MODEL_CACHE --container CONTAINER --split holdout
```

Adoption recomputes every score and aggregate from the 120 hash-bound original dev packets and the forty original dev references, then selects highest Recall@8, then MRR@8, then bm25/vector/rrf order on exact ties. It copies the measured rows/latencies into canonical `evaluation/results/dev.json` and derives `strategy-selection.json`, without retrieval or new measurements. Original dev packets stay in place; their prior canonical directory is untouched. Before replacing either canonical file, it preserves its exact original bytes under `evidence/evaluation-binding-repair-r1/baseline/`. The selected dev score is diagnostic; the acceptance thresholds apply to holdout, so dev Recall below .9 does not prevent adoption.

Before any holdout reference read or retrieval, the evaluator reconstructs that same pinned winner, checks active strategy/profile/configuration, pinned original helper snapshots, current evaluator/retriever sources, original corpus inputs/source files, and every frozen BGE artifact. The model-cache argument must resolve to the original observation's cache path; HF snapshot symlinks may resolve only inside that cache. It writes an exclusive `holdout.experiment.json` claim and fsyncs its file and parent directory before opening canonical references. A process death or partial observation leaves this claim; replay rejects before reference reads or retriever creation. A claimed or incomplete observation requires reconciliation, never another holdout run.

Holdout retrieval, readiness and `full-rag-gate.json` must carry the same `strategy`, `retrievalConfigVersion`, `profileHash`, `retrieverSourceHash`, `evaluatorSourceHash`, `modelCacheHash` (the canonical hash of the frozen BGE artifact map), and canonical `selectionHash`. The retrieval report additionally binds `experimentHash` to its original pre-query claim. All consumers rederive the selected strategy from the original dev observations and recheck the active profile; a caller cannot choose `rrf` or substitute a profile/configuration. The full gate uses only canonical `evaluation/results/holdout.json` and `evaluation/results/readiness-holdout.json`, plus the exact supervisor-pinned reference review. This remains a retrieval/readiness prerequisite; adoption alone does not produce a full-RAG PASS.

## Execution and bounded repair

The only common stage names under `authoring-batches/bNNN/` are `generate-1`, `review-1`, `repair-generate-1`, `repair-review-1`. `attempt=1` is the existing transport argument; the two generation stage names encode the single original plus single repair budget. Before transport, a frozen `<stage>.intent.json` binds plan, batch, UIDs and prompt/schema hashes. A touched stage without a valid completed original receipt is unknown and blocks new requests. Existing stages validate prompt/schema/input/output/events/stderr hashes, actual invocation, subscription/model/high-effort settings and separate ephemeral workspaces. Other namespaces and per-card execution folders are rejected. Unknown/auth/quota/transport errors stop the run; completed content failures may allow other batches to proceed.

Original generation covers every batch UID exactly once. Only structurally valid objects receive the first independent review. Immutable `repair-authorization.json` binds the original shared generation/review receipts, exact failed objects/errors and failed UID subset. Only this subset gets one new generation and independent re-review. Original passing objects remain unchanged. There is no third generation, automatic transport retry, model fallback or replacement run namespace. A completed malformed repair wrapper (wrong UID, cardinality or order in generation or review) fails only the authorized repair subset; original independent PASS siblings still verify from their unchanged original objects/receipts. Unknown transport outcomes still block globally and never authorize another generation. Persistent content failures are recorded in `quarantine.json` as `INCOMPLETE`, with actual failed UIDs. Their available final candidate/review objects are retained; no PASS marker is written for them.

## Exporter and MCP contract

A passing UID has these files:

```
authoring/<uid>/candidate.json
authoring/<uid>/review.json
authoring/<uid>/verified.json
```

The first two are exact parsed objects from the original shared `result.json` arrays. `verified.json` contains `mode='batch-v1'`, `stableUid`, `batchId`, `planHash`, `goalHash`, `packetHash` (the packet's existing internal hash), `packetObjectHash`, `packetFileHash`, `candidateObjectHash`, `reviewObjectHash`, `budget={initial:1,repair:0|1,limit:2}`, optional repair authorization hash, `verdict='PASS'`, `reviewedBy='codex'`, `humanPerCardReview=false`, and shared `generation`/`independentReview` references. Each reference contains the original common result/execution/invocation/prompt/schema paths plus result/execution/invocation/events/stderr hashes. Paths are constructed from known batch/stage names and restricted under control; arbitrary record-supplied references are never dereferenced. Requested model is `gpt-6-sol`; unknown actual reported models remain JSON null.

Call `verify_record(root, corpus_root, catalogue, uid)` before consuming a `batch-v1` marker. It returns `(candidate, review, metadata)` and performs no model calls. It reloads the frozen global plan/current catalogue and packet, validates official source provenance with the existing validator, replays original common receipts and exact projected prompts, reconstructs the authorized repair subset, runs every per-card structural and independent-review gate, and requires exact final object/metadata equality. File presence, copied hashes or a shared batch verdict alone are insufficient. A failed/missing/tampered/unknown record raises instead of becoming publishable. Original passing cards can still verify when a sibling has a *known* persistent content failure.

`summary(root, corpus_root, catalogue)` also makes no requests. It returns `total=337`, verified count, `old334Total=334`, old verified coverage, incomplete UIDs, invalid records and `verdict`. Only all 337 verified cards plus exact old334 coverage produce deck `PASS`; canary completion remains `INCOMPLETE`. Consumers should use this function rather than interpreting individual CLI receipts as per-card executions.
