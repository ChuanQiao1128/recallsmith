## [major] App has Cognito sign-up but no working in-app account deletion (Guideline 5.1.1(v))

镜头：`Lens 3`　原始初评：blocker

**证据**

```
App.tsx:257-259 registers the real auth flow (`<Stack.Screen name="SignUp" component={SignUpScreen} />`, `ConfirmSignUp`), and src/auth/authStore.ts:152 calls Amplify `signUp({...})` — so the app supports account creation. The only reachable settings tree is `Settings` (App.tsx:256), whose account UI is src/features/gacha/settings/account/AccountSection.tsx:13-16, offering exactly `signOut: 'Sign out'`, `freshStartTitle: 'Fresh Start'` (freshStartBody: "Clear today's schedule. Keeps your owned cards.") and `resetSchedule: 'Reset review schedule'` — no deletion. The only "Delete account" UI is src/screens/DeleteAccountConfirmScreen.tsx:35-36, whose button is `primaryLabel="Delete account data"` with `onPrimary={() => navigation.navigate('Welcome')}` — it deletes nothing, and its numbers come from `DELETE_PREVIEW` in src/mock/settings.ts:16-21 (hardcoded cards:133, streak:4). That screen is unreachable from the real app: `rg "navigate\('SettingsMain'\)"` returns hits only from inside the mock island itself (SettingsAudienceScreen.tsx:33, SettingsPoolsScreen.tsx:31, …
```

**用户影响**：A reviewer creates an account with email/password, goes to Settings looking for account deletion as required, and finds only Sign out. Apple rejects under 5.1.1(v) (apps supporting account creation must offer in-app account deletion). If the reviewer instead reaches the mock screen, it is worse: a button labelled "Delete account data" that silently navigates to Welcome and deletes nothing is a functional misrepresentation. Existing users who want their Cognito account erased have no way to do it.

**建议修法**：Add a real deletion entry to AccountSection (the reachable one) that calls Amplify's `deleteUser()` from `aws-amplify/auth`, clears local progress/drawState storage, then signs out — behind a typed confirmation. Delete the unreachable mock island (SettingsMainScreen/SettingsAccountScreen/DeleteAccountConfirmScreen + src/mock/settings.ts) so the fake delete button cannot be reached or revived.

## [major] Auto-renewable subscription paywall shows no price and has no Terms of Use (EULA) link (Guideline 3.1.2)

镜头：`Lens 3`　原始初评：blocker

**证据**

```
src/screens/PaywallScreen.tsx:209-212 is the entire billing disclosure: `<Text style={styles.kLabel}>Billing</Text>` / `<Text style={styles.kValue}>Monthly subscription</Text>` — a duration word and nothing else. `rg -ni "priceString|price" src/screens/PaywallScreen.tsx` returns zero matches, and `rg -n "priceString|localizedPrice" src/premium/revenuecat.ts` also returns zero, so the localized price from the RevenueCat `PurchasesPackage` is never rendered anywhere. The purchase button at PaywallScreen.tsx:255-257 ("Unlock Premium") goes straight to `handleSubscribe()` → `Purchases.purchasePackage(pkg)` (src/premium/revenuecat.ts:398). App-wide, `rg -ni "terms.?of.?(use|service)|eula" src App.tsx` returns nothing — there is no EULA link in the binary at all. A privacy policy link does exist, but only in Settings (src/screens/SettingsScreen.tsx:51, a Notion URL) and not on the paywall (src/features/gacha/settings/about/AboutSection.tsx:11).
```

**用户影响**：A reviewer opens the paywall and is asked to buy a recurring subscription without ever being shown what it costs per month, and with no link to the Terms of Use. This is one of the most commonly enforced rejections for subscription apps — Apple requires the paywall itself to state title, duration and price per period, and to carry functional Terms of Use (EULA) and Privacy Policy links. Real users also hit Apple's purchase sheet as the first place a price appears.

**建议修法**：In PaywallScreen, read the current package (already fetched via `Purchases.getOfferings()`, revenuecat.ts:395) and render `pkg.product.priceString` plus the period next to the "Billing" row, and add two `Linking.openURL` links on the paywall — Terms of Use (Apple's standard EULA URL is acceptable) and the existing Notion privacy-policy URL from SettingsScreen.tsx:51.

**用户影响**：An upgraded user with, say, 40 drawn-but-unstudied cards hits one AsyncStorage read failure (disk pressure, backgrounded mid-read). resolveEffectiveOwned returns only their already-studied uids. ## [minor] The economy floor's marker-before-wallet ordering has NO application-layer recheck — a failed wallet write soft-locks a starved user until local midnight

镜头：`Lens 5`　原始初评：major

**证据**

```
src/features/gacha/rewards/economyFloor.ts:140-141 writes the day marker first and the wallet second. The idempotency read that guards the retry is src/features/gacha/rewards/economyFloor.ts:118-121: `const marker = await AsyncStorage.getItem(key); if (marker === dayKey) { return { wallet, granted: 0, reason: 'already-granted-today' }; }` — it returns before ever consulting the wallet, so a marker present with an unpaid wallet is indistinguishable from a marker present with a paid one. The `catch` at economyFloor.ts:144-148 swallows the failed `saveRewardWalletState` and returns `granted: 0` with no compensation. The repo's own test codifies the un-recovered state rather than covering it: tests/unit/economyFloor.test.ts:142-163 fails the wallet setItem, then asserts `expect(store.get(MARKER_KEY)).toBe('2026-08-19')` and, on retry, `expect(retry.granted).toBe(0); expect(await loadRewardWalletState()).toEqual(EMPTY);`. Nothing else in the app grants a pull to this user: the only other faucets are `seedStarterPullsIfNeeded` (one-shot, flag already set), `applySessionRewardToWallet` …
```

**用户影响**：An AsyncStorage write failure (disk pressure, an iOS jetsam kill in the window between the two awaits) at the moment the floor pays out leaves the user with 0 owned-unlearned cards, 0 due, and 0 pulls. Home renders the draw CTA as `state: 'locked'` with the copy "Clear today's route to unlock pulls" (src/features/gacha/selectors/homeSelectors.ts:225-228) — instructing them to clear a route that is empty. There is no study to do, no pull to spend, and no in-app recovery until the local day rolls over. That is the exact dead end the floor was written to prevent, and the app is inert for the rest of the day. Low trigger rate, but zero recovery and no visible cause when it fires.

**建议修法**：Make the marker record what was actually paid, not just when. Either write the marker only after `saveRewardWalletState` resolves and accept the (already-tested) double-grant risk, or — better — keep the current order and add the missing recheck at economyFloor.ts:119: when `marker === dayKey`, still re-read the wallet and, if `availablePulls + reservePulls === 0`, complete the interrupted grant instead of returning `already-granted-today`. The per-day marker still caps it at one pull.

镜头：`Lens 5`　原始初评：major

**证据**

```

On the NEXT launch the seed finally runs for that account and hits src/features/gacha/rewards/rewardWallet.ts:176-180: `const isEmpty = current.availablePulls === 0 && current.reservePulls === 0; if (!isEmpty) { …
```

**用户影响**：The common onboarding path — open the app anonymously, then create an account or sign in without relaunching — leaves the new account with 1 pull instead of 3, permanently. # 三、本版零真机验证 — 上传后按此顺序排查

We are shipping a release whose central mechanic — an ownership gate wired into five screens — has never been rendered on a physical device. Everything below is knowingly unverified.

**Look at these after upload, in this order, on a real phone that was running 1.4.0 before:**

1. **Home, first launch after upgrade.** The highest-consequence unverified path. `deckActionResolver.ts:204` now does a per-deck `loadDrawState` where 1.4.0 did none. Confirm fresh/due counts are non-zero and the draw CTA is not stuck on `state: 'locked'` with "Clear today's route to unlock pulls" (homeSelectors.ts:225-228). Also unmeasured: first-load jank from that read amplification.
2. **Library, immediately after.** The fail-closed gate's blast radius. If an AsyncStorage read hiccups, tiles you own flip to "Missing" silhouettes (`libraryMapper.ts:120-131`) because `drawStateStore.ts:226` returns `{ owned: [] }` instead of null. It self-heals on the next focus, but if a tester reports "my collection shrank", this is the cause and it is finding #1, not a data loss.
3. **Draw → open 10 → ceremony.** Even with FIX 1 the user is still not *told* they got fewer cards than requested — `poolExhausted` has zero consumers outside tests and is not forwarded into the DrawCeremony params (DrawScreen.tsx:544-557). Verify a short pack plays cleanly and the wallet math reads right.
4. **CardDetail from a Library tile.** `CardDetailScreen.tsx:45-52` `catch { return []; }` defeats its own fail-open wrapper — a failed progress read locks a card the Library just rendered as Learning. Two taps, two contradictory answers on the same card. Also the only screen with four new dynamic `import()` calls, whose behaviour under a **release** Metro bundle is unverified.
5. **Sign in from a signed-out upgraded account.** Drawn-but-unstudied cards do not follow you across the sub partition — there is no draw-state equivalent of `adoptPendingProgressEvents` (`progressSync.ts:580-602`), and the gap is admitted in-comment at `drawStateStore.ts:44-48`. Studied cards come back via grandfathering; unopened pulls do not. Signing out restores the anon scope intact.
6. **Paywall.** Not because of code — it is unchanged — but because it is where a reviewer will look. No price string, no Terms of Use link anywhere in the binary (`rg -ni "priceString|terms.?of.?(use|service)|eula" src App.tsx` → 0 hits, confirmed by me). If this build gets rejected, this is overwhelmingly the reason.

**Unverifiable, accepted:** EAS server-side `production` environment values (there is no `.env` in the repo and CI injects no `EXPO_PUBLIC_*`, so those exist only in EAS — check `eas env:list --environment production` yourself before pressing build; I am not permitted to run eas). Whether SDK 54's prebuild emits `PrivacyInfo.xcprivacy` into the .ipa. The server side of `/api/v1/draw-state/sync`, which decides whether a reinstall recovers a collection at all. Actual Hermes bytecode behaviour.

**Live remote config is safe and I checked it:** the served `minSupportedVersion` is 1.3.0, comparison is numeric not string, and every failure path fails open. 1.5.0 will not force-update-brick itself.
