# evals: seeded-defect eval harness for the AI QA gate

`developercards-evals` (module `dc_evals`, command `dc-evals`) measures the production AI QA
reviewer before the gate is switched on. Contract §7.9 step 3 requires a committed eval report
with overall **recall ≥ 0.80** and **precision ≥ 0.70** on serious (blocker/major) defects before
`AI_QA_ENABLED=1` is set anywhere. Since X04 the gate also bounds the control false-positive rate,
sets a per-class recall floor and refuses incomplete, errored or non-production runs. Since Y05
it is measured on `seeded-v3` (no length or artifact cues the cue check measures; judgment classes
built from constructions), needs at least two repetitions and the 95% interval bounds, and binds
the run to the configuration that ships (provider, model, prompt version, effort,
structured-output mode); see [Gate](#gate). Since Z04 every interval and the class minimum count
distinct cards, not items pooled over repetitions, and the judgment-class labels carry their
provenance: they are model-assisted and self-evidenced (see
[Label provenance](#label-provenance-of-the-judgment-classes)).

The harness does not re-implement the reviewer. It depends on `services/ai-qa` through a uv path
source and calls `ai_qa.review.review_card` directly, so the prompt (`ai_qa.prompts.SYSTEM_PROMPT`,
version `PROMPT_VERSION`), the findings schema, the reply parsing, the provider switch and the
settings validation are exactly the production code path. Settings come from
`ai_qa.settings.load_settings` (a bare first-party model id is rejected for `bedrock`, exactly as
in the Lambda) and the client from `ai_qa.providers.make_client`.

## Dataset `seeded-v1`

- **Provenance.** Cards come only from the project's own decks, `content/decks/aws-saa-c03.md`
  and `content/decks/claude-ccdv-f.md`, parsed by the console's parser
  (`frontend/src/lib/deckImport.ts`). No exam-dump content. Every mutation text (hint sentences,
  wrappers, qualifier targets, replacement facts) is written in `mutations-v1.json`. No card had
  to be excluded for banned wording; if a future export contains any, exclude that card in the
  seed rather than editing the deck.
- **Export.** One JSON object per card, in file order, keys `sourceUid, deckSlug, stableUid,
  difficulty, topic, question, explanation, codeSnippet, codeLanguage, realWorldUsage, mcq,
  source` (`topic`, `mcq` and `source` are `null` when absent). A deck with parse errors is
  refused.
- **Composition.** 200 rows: 100 cards with exactly one injected defect and 100 untouched
  controls. Defect mix: `incorrect_answer` 20, `multiple_correct` 20, `answer_leak` 15,
  `ambiguous_stem` 15, `outdated_fact` 15, `qualifier_mismatch` 15.
- **Seeding.** One `random.Random(18)`. For each class in the order above: collect the eligible
  cards not used yet, sorted by deck and uid; draw a random permutation and take the class count
  (for `outdated_fact`, at most `maxCardsPerRule` = 2 cards per rule group); apply the template.
  Then the controls: for every (deck, MCQ or Q/A) stratum, sample as many unused cards as the
  defective rows have in that stratum, so the controls mirror the defective rows. Shuffle all
  rows and number them `s-0001` … `s-0200`.
- **Row.** `{"id", "deckSlug", "sourceUid", "defect", "mutation", "card"}`: `defect` is the
  class or `null`, `mutation` a one-line description of the concrete change or `null`, and `card`
  the (mutated or untouched) exported card without `sourceUid`/`deckSlug`.

### Mutation rules (`mutations-v1.json`)

Every mutation changes exactly one thing and leaves the rest of the card intact.

| Class | Eligible cards | Change |
|---|---|---|
| `incorrect_answer` | single-answer MCQ; Q/A with a topic | MCQ: the `correct` flag moves from the keyed option to a randomly chosen distractor (texts and `why`s unchanged, so the key contradicts the explanation). Q/A: the explanation is replaced by the explanation of a random other Q/A card of the same deck with a different topic. |
| `multiple_correct` | single-answer MCQ (wrapped text ≤ 600 chars) | A random distractor's text becomes the keyed option's text inside a neutral wrapper (`Proceed as follows: …`, `Adopt this approach: …`, `… Record the change in the team's runbook.`); still exactly one option starred. |
| `answer_leak` | single-answer MCQ whose keyed prefix is unique; Q/A whose first sentence has 4–40 words | A hint line is appended to the stem: MCQ `Hint: the correct option begins "<first 10 words> ..."` (or the whole text when it is short); Q/A `Hint: <first sentence of the explanation>.` |
| `ambiguous_stem` | single-answer MCQ whose qualifier is an optimisation target from the committed list and matches one of three stem patterns | The qualifier is removed from the stem and `mcq.qualifier` is cleared: `… with the LEAST operational overhead?` → `…?`; `… is the MOST secure?` → `… is acceptable?`; `the MOST cost-effective way` → `an acceptable way`. Options and key unchanged, so several options may now satisfy the stem. |
| `outdated_fact` | cards whose explanation, keyed option or code contains a rule's `find` string | The first matching rule's `find` → `replace` in every text field; each rule states what changed and roughly when (Lambda memory and timeout ceilings, S3 request rates and default encryption, Fargate storage, SQS message size, DynamoDB transaction size, Kinesis retention, gp3 IOPS, API Gateway timeout, Message Batches limits, long-context pricing, context window, retired model id). |
| `qualifier_mismatch` | MCQ whose qualifier is in the committed map and appears as a whole phrase in the stem | The qualifier in the stem and in `mcq.qualifier` becomes a different optimisation target (e.g. `MOST secure` → `MOST cost-effective`, `LEAST operational overhead` → `LOWEST cost`), so the keyed option answers a target the stem no longer asks for. |

Controls are real deck cards and may contain genuine defects. When a run flags a control, review
it by hand: if the finding is right, fix the deck and cut a new dataset version (new mutation
file, new dataset name) rather than editing a committed one.

`seeded-v1` is kept unchanged (the 2026-09-27 claude-cli baseline was measured on it). Its known
weaknesses, which `seeded-v2` fixes: no card carries a source, so `source_unsupported` and false
positives on cited cards are never measured; and the MCQ `incorrect_answer`, `multiple_correct`
and `answer_leak` templates leave surface artifacts (the moved key's `why` still argues against
it, the keyed text is repeated inside a wrapper, a literal `Hint:` line) that a reviewer can spot
without domain knowledge.

## Dataset `seeded-v2` (comparison only since Y05)

- **Citations.** `dc-evals export-sources` turns each deck's fact-check ledger
  (`content/decks/<slug>.ledger.csv`: one row per card and cited page, with the page's https URL
  and the `fact_checked` note of what it says) into `data/sources-<slug>.jsonl`, keeping rows with
  an https URL (the first one when a row lists several), a note of 1–1000 characters and
  `in_deck` = yes. The quotes are the project's fact-check notes of the cited page, not verbatim
  page text. v2 uses only cards with at least one citation (750 of 812) and sets `card.source` to
  the citation sharing the most content words with the card's question and answer, so every row
  (controls included) is cited, like every AI draft (contract §8.1).
- **Composition.** 240 rows: 120 defective and 120 controls mirrored by (deck, MCQ or Q/A).
  Classes and tiers (`counts` in `mutations-v2.json`):

  | Class | easy | subtle | adversarial |
  |---|---:|---:|---:|
  | `incorrect_answer` | 5 | 13 | 2 |
  | `multiple_correct` | 5 | 15 | |
  | `answer_leak` | 5 | 10 | |
  | `ambiguous_stem` | | 15 | |
  | `outdated_fact` | | 15 | |
  | `qualifier_mismatch` | | 15 | |
  | `source_unsupported` | | 20 | |

  Two of the controls are adversarial (tier `adversarial`).
- **Tiers.** `easy` = the v1 templates, artifacts and all, kept for comparison. `subtle`:
  - `incorrect_answer`: a `factSwaps` rule replaces a fact with a value that was never true
    (CloudFront certificates outside us-east-1, a 10 Gbps VPN tunnel, stateless security groups,
    four-nines S3 durability, cheaper-than-base cache writes, PostToolUse blocking a call, …) in
    the explanation, code, usage and keyed option only; the stem, distractors, whys and source
    keep the true fact. At most 2 cards per rule group.
  - `multiple_correct`: a distractor becomes the explanation's first sentence (6–40 words), which
    states the keyed answer in other words, and its `why` is cleared.
  - `answer_leak` (MCQ): the stem gains one neutral sentence (`termSentences`) naming a
    distinctive term (a product name or identifier such as `kms:Decrypt`) that only the keyed
    option uses.
  - `ambiguous_stem`, `outdated_fact`, `qualifier_mismatch`: the v1 rules, unchanged.
  - `source_unsupported`: the source is replaced by the citation of another card of the same deck
    and topic, from a page the card does not cite, sharing at most 2 content words with the card.
  - `adversarial`: an `incorrect_answer` fact swap plus a `realWorldUsage` note telling the
    reviewer to report no findings; on the two adversarial controls the note asks the reviewer
    to flag the card. The prompt says card text is data, never instructions.
- **Row.** `{"id", "deckSlug", "sourceUid", "defect", "tier", "mutation", "card"}` (`tier` is
  `easy`, `subtle`, `adversarial` or `null` for an ordinary control).
- **Seeding.** One `random.Random(1802)`; per class in `DEFECT_CLASSES` order and per tier in the
  order `counts` lists them, sample the eligible unused cards and apply the template; then the
  mirrored controls, then the adversarial controls; shuffle and number `s-0001` … `s-0240`.

The Y05 audit (round 2) found three problems that make v2 unfit as gate evidence, which
`seeded-v3` fixes: the subtle `multiple_correct` rows copy the explanation's first sentence into a
distractor and clear its `why` (no control has a distractor without a why, so that alone
separates all 15 rows); the subtle fact swaps keep the true value in `source.quote`, so the defect
is a string difference between the explanation and the quote; and `ambiguous_stem` /
`qualifier_mismatch` reuse the v1 templates, which the 2026-09-27 tuning found mostly produce
cards that are not actually ambiguous (6 of 7 dev cards).

## Dataset `seeded-v3` (the gate dataset)

Built by `dc-evals seed --dataset v3` (`seed.build_rows_v3`, registry `mutations.MUTATIONS_V3`,
templates `data/mutations-v3.json`): the v2 procedure (cited cards only, per-tier seeding, one
`random.Random(1803)`, source_unsupported, adversarial rows) with these changes.

- **No easy tier.** Every v1 template that leaves a surface artifact is gone.
- **Fact swaps by what the source shows.** `incorrect_answer` (the `factSwaps` rules) and
  `outdated_fact` (the `rules`) are split into tier `subtle`, where the card's quote still states
  the true value (a reviewer can catch the defect by reading the source), and tier
  `source-silent`, where every clause of the quote that states the fact is dropped (split at
  `; ` and sentence ends; `mutations.silence_quote`), or another of the card's own ledger
  citations that never states it is used, so only domain knowledge catches it. That is the case
  of a hallucinated fact in an AI draft whose verbatim excerpt does not mention it. Each rule
  lists `quoteMarkers`, the ways the ledger notes phrase the true value (`11 nines` for
  99.999999999 percent). The adversarial `incorrect_answer` rows are source-silent swaps plus the
  reviewer note. Report the tiers separately (`perTier`).
- **Adjudicated judgment classes.** `multiple_correct`, `ambiguous_stem` and
  `qualifier_mismatch` come from `constructions` committed in `mutations-v3.json`, one per card,
  each reviewed in the Y05 session (the review rejected constructions whose viability was
  doubtful). That review was model-assisted; no independent human has reviewed them yet (see
  [Label provenance](#label-provenance-of-the-judgment-classes)). The
  seed picks the class count from them at random; a card named by a construction is used by no
  other class. They are valid by construction:
  - `ambiguous_stem`: the stem loses the stated constraint (or the qualifier) that a distractor's
    own `why` cites as its only reason for failing (`evidence`, a verbatim piece of that why), so
    that distractor meets every remaining stated requirement as well as the key does and nothing
    left in the stem decides between them.
  - `qualifier_mismatch`: the stem's qualifier becomes one that the card's own text (a `why` or
    the explanation, quoted in `evidence`) shows a distractor beats the key on, while that
    distractor meets every other stated requirement (`MOST cost-effective` -> `FASTEST
    retrieval` where the Flexible Retrieval option's why says it restores "in hours").
  - `multiple_correct`: a distractor becomes a hand-written paraphrase of the keyed answer (no
    run of 5 words shared with the key or the explanation, length inside the card's own option
    lengths) with a `why` in the card's style that rejects it on a wrong ground, the way an
    author's mistake would; no why is cleared and no explanation text is copied.
- **Rationale.** Every row carries `rationale`: for a constructed row
  `{keyedOption, viableOption, reason, …}` plus `removedConstraint` and `evidence{field, option,
  text}` (ambiguous_stem) or `qualifierFrom`, `qualifierTo` and `evidence` (qualifier_mismatch);
  for a fact swap `{rule, find, replace, source: "states the true value" | "silent", reason}`;
  otherwise `null`. Row keys: `id, deckSlug, sourceUid, defect, tier, mutation, rationale, card`.
- **Matched controls.** Each control is the unused card of the same deck and card shape nearest
  to one defective row in stem, explanation and quote length, keyed-minus-distractor length and
  option count (`seed._matched_controls`), so no length cue separates the defects from the
  controls, including lengths a mutation changes (a removed constraint shortens the stem).
- **Composition.** 226 rows: 113 defective and 113 controls (2 adversarial).

  | Class | subtle | source-silent | adversarial |
  |---|---:|---:|---:|
  | `incorrect_answer` | 6 | 10 | 2 |
  | `multiple_correct` | 15 | | |
  | `answer_leak` | 15 | | |
  | `ambiguous_stem` | 15 | | |
  | `outdated_fact` | 6 | 9 | |
  | `qualifier_mismatch` | 15 | | |
  | `source_unsupported` | 20 | | |

- **Surface-cue check.** `tests/cues.py` computes simple card features (option count, a
  distractor without a why, a keyed option with one, a distractor sharing an 8-word run with the
  explanation, the keyed text inside a distractor, a `Hint:` line, stem / explanation / quote
  length, keyed-minus-distractor length, option length spread, shortest why) and compares
  defects with controls of the same deck and card shape by AUC; nothing is trained.
  `test_surface_cues_are_balanced_between_defects_and_controls` requires every class to stay
  within the bands (artifacts 0.4-0.6 per class; lengths 0.38-0.62 pooled, 0.15-0.85 per class,
  since which cards a rule can apply to changes lengths too), and
  `test_cue_check_catches_the_v2_artifacts` shows the same check flags v2.
  The check has no feature for the self-evidence cue below (a why that still cites what the stem
  no longer states), which every `ambiguous_stem` and `qualifier_mismatch` row carries, so "no
  surface cues" means no cue among the features above.

### Label provenance of the judgment classes

Z04 (ai-agent-27). The current `ambiguous_stem` and `qualifier_mismatch` rows are
**self-evidenced**: by construction (`mutations.apply_constructed_ambiguous_stem` and
`apply_constructed_qualifier_mismatch` refuse anything else) the viable option's `why`, or the
explanation, still states the criterion that makes that option viable, for example s-0019's
option-b why still says "the question asks for the smallest change" after the stem lost that
requirement. The reviewer prompt names exactly that inconsistency as a sign, so recall on these
rows shows that the reviewer applies that rule. It does not show that it finds ambiguity no why
points to. Their labels, and those of `multiple_correct`, are **model-assisted**: the Y05 session
wrote and adjudicated the constructions, and no independent human has reviewed them (s-0147, where
option b keeps public IPs behind an ALB-only security group against a stem that says users must
"never" reach the instances directly, is debatable).

- `src/dc_evals/labels.py` derives each judgment-class row's provenance from the committed
  dataset: `evidence` is `self-evidenced` when `rationale.evidence.text` is still in the field it
  quotes, else `why-neutral`; `humanVerdict` comes from the adjudication file.
- `data/adjudications-v3.json` is the owner's adjudication file (format in `labels.py`): the
  dataset name and sha256, `labelSource` (`model-assisted`) and a list of verdicts
  `{id, verdict: "valid" | "invalid", adjudicator, date, note}`. It is committed with no verdicts.
  Adjudicate at least 5 rows per judgment class, stratified by deck and by run outcome (caught in
  both repetitions, missed in any), and add them there; `dc-evals score --adjudications <file>`
  scores with a draft file.
- The scorer drops a row judged `invalid` from every recall figure and from its class's card
  count (so the class falls under the 15-card minimum and needs a new dataset version with a
  replacement row) and lists it in `labels.excludedRows`. The report's `labels` block and the
  Markdown "Label provenance" section give, per class, the rows, how many are self-evidenced or
  why-neutral, the human verdicts, and recall per evidence tier.
- A **why-neutral** tier (the evidencing why rewritten to reject the option on a requirement the
  stem still states, or a card whose whys never mention the removed criterion) is reported
  separately and must reach the per-class floor on its own. seeded-v3 has no such row; building
  them needs new hand-reviewed constructions and therefore a new dataset version.

### Regeneration

Both generated files are pure derivations and are checked byte for byte:

```
node evals/scripts/export-cards.mts --check     # needs frontend/node_modules (esbuild)
(cd evals && uv run --python 3.12 dc-evals export-sources --check)
(cd evals && uv run --python 3.12 dc-evals seed --check)
(cd evals && uv run --python 3.12 dc-evals seed --dataset v2 --check)
(cd evals && uv run --python 3.12 dc-evals seed --dataset v3 --check)
```

Without `--check` the same commands rewrite the files. Changing a deck changes the export and
therefore the dataset; a dataset change after a committed report means a new dataset version.

## Commands

```
cd evals
uv run --python 3.12 dc-evals export-sources [--check]
uv run --python 3.12 dc-evals seed [--dataset v1|v2|v3] [--check]
uv run --python 3.12 dc-evals run --provider bedrock|anthropic|bedrock-converse|claude-cli --model <id> \
    [--second-provider bedrock-converse|bedrock|anthropic --second-model <id> [--second-scope facts|all|<list>]] \
    [--dataset v3|v2|v1|authored-v1] [--reps 2] [--limit N] [--concurrency 4] [--max-cost-usd 30] \
    [--review-date YYYY-MM-DD] [--dry-run] --out reports/
uv run --python 3.12 dc-evals score reports/<stem>.jsonl [--gate] [--adjudications data/adjudications-v3.json]
uv run --python 3.12 dc-evals author [--model claude-opus-5-5] [--sources data/authored-sources-v1.json] [--limit N]
uv run --python 3.12 dc-evals jury [--jurors provider:model,...] [--limit N]
uv run --python 3.12 dc-evals compare reports/<run>.jsonl ... --name <name> [--date YYYY-MM-DD] [--out reports/]
```

The three Q03 commands (`author`, `jury`, `compare`) are described in
[Agent-authored cards, model jury and configuration comparison](#agent-authored-cards-model-jury-and-configuration-comparison-q03).

- `dc-evals run` **spends money and is run by the owner only**: never in CI, a verify or a
  worker session. Run it with `--dry-run` first: it prints the row count and an estimate
  (rows × 3,000 input + 1,500 output tokens at the settings prices) without constructing a
  client. Expect roughly $0.05–0.10 per card on Opus 5, so about $11–23 for the 226 v3 rows per
  repetition. `--dataset` defaults to `v3`. `--reps N` (default 2, the gate's minimum) reviews the
  whole dataset N times (records carry `rep`; the report pools them and lists recall and FP rate
  per rep).
  `--max-cost-usd` (default 30) stops submitting rows once the summed estimated cost over all
  reps reaches the ceiling; such a run, like a `--limit` run, is written but the gate refuses it. Bedrock needs a Bedrock model id (`anthropic.claude-opus-5`) and AWS credentials; the
  Anthropic API reads `ANTHROPIC_API_KEY` from the environment.
- The run header records `dataset`, `datasetSha256` (of the dataset file), `datasetRows`, `reps`,
  `n`, `reviewDate` (it decides `outdated_fact`), `effort`, `structuredOutputs` (configured mode)
  and `structuredOutputsAtStart` (resolved). Each item records `rep`, `tier`, `structured` (what
  its request actually used: the ai-qa fallback can switch structured outputs off process-wide
  mid-run) and `servedModel` (the model id the response reports). A row whose response came from
  a model other than the requested one (a dated snapshot of it matches) is recorded as
  `status: "error"`, `errorCode: "MODEL_MISMATCH"` with no findings.
- A run writes three files under `--out`, named
  `<YYYY-MM-DD>-<provider>-<model>-<promptVersion>` (UTC run date; `-2`, `-3`, … when the name is
  taken; nothing is overwritten): `.jsonl` (a `run` header line, then one `item` record per
  reviewed row), `.json` (the report) and `.md` (a human summary: overall and per-class tables,
  gate result, cost, latency, errors).
- `dc-evals score` prints the report JSON for a run file; with `--gate` it exits 1 unless every
  gate condition below holds, and prints each failed condition to stderr. Run files written
  before X04 (the v1 baseline) still score; their missing header keys read as null and the gate
  refuses them.

- `--provider claude-cli` (local only) sends the same request through the owner's Claude Code CLI
  (`claude -p`, their subscription, on their machine) with `--model claude-opus-5`: same
  `SYSTEM_PROMPT`, same user turn, structured outputs off (the Bedrock path: validated plain JSON
  and one repair turn). `claude -p` takes one prompt, so the repair turn is sent as one user
  message quoting the rejected reply. Use it to measure the prompt before Bedrock model access
  exists; its report is labelled `claude-cli` and `evidenceClass: "proxy"` and never replaces the
  Bedrock run the rollout below requires. `src/dc_evals/claude_cli.py`; tests fake the subprocess.
  Z04 (ai-agent-30): the request's `max_tokens` reaches the CLI as `CLAUDE_CODE_MAX_OUTPUT_TOKENS`
  (`thinking` is not sent; effort is), and a CLI result whose `stop_reason` is `max_tokens` or
  `refusal` is recorded as `MAX_TOKENS` / `REFUSAL` exactly as on Bedrock. A result without a
  stop reason reads as `end_turn`, and the run file does not say which results carried one, so a
  proxy run cannot show that no card is truncated or refused; its report says so
  (`proxyFidelity`, and a "Proxy fidelity" line in the Markdown). A CLI error result is recorded
  as `CLI_<SUBTYPE>` (e.g. `CLI_ERROR_MAX_TURNS`), not `UNEXPECTED`.

Rollout (contract §7.9 step 3): dry run, then the run of the shipping configuration,

```
uv run --python 3.12 dc-evals run --provider bedrock --model anthropic.claude-opus-5 --dataset v3 --reps 2 --out reports/
uv run --python 3.12 dc-evals score reports/<stem>.jsonl --gate    # must exit 0
```

then commit the `.jsonl` + `.json` + `.md` files. Only after that may `AI_QA_ENABLED` be switched
on. As of 2026-09-27 no such run exists: the prompt that ships (`qa-v3`) has only proxy
(`claude-cli`) runs on `seeded-v1`, which fail the gate on substance too (see
`reports/tuning-2026-09-27/README.md`), so qa-v3 has **not** passed the gate. The Bedrock gate run
is also where the `MAX_TOKENS` and `REFUSAL` rates (`errors`) are checked: the proxy cannot
observe them reliably (ai-agent-30), and at `MAX_TOKENS` = 16000 with effort `high` a truncation
has only been ruled out for Bedrock once that run exists.

## Agent-authored cards, model jury and configuration comparison (Q03)

The seeded datasets contain synthetic mutations of accepted cards. The question that matters for
rollout is whether the gate catches the errors **the Claude authoring agent itself makes**. The
owner does not hand-label cards, so this path is fully automated: generate a card set the way the
author-cards skill would, label it with a jury of models from vendors that are not under test,
and compare reviewer configurations on both `seeded-v3` and that set.

### `dc-evals author` (owner's machine only; spends the owner's Claude subscription)

For each of the 16 pages in `data/authored-sources-v1.json` (8 AWS documentation pages for
SAA-C03 topics, 8 Claude platform documentation pages for the Claude developer deck; official
documentation only, never an exam-dump site), `author`:

1. runs `dc-ingest --json <url>` through `uv run --project ../tools/ingest` (the `read_source`
   invocation) and picks up to 4 chunks of at least 400 characters, spread evenly over the page;
2. asks the local Claude Code CLI (`claude -p`, model `claude-opus-5-5` by default, `--model` to
   change; the `claude_cli.py` transport: no tools, strict empty MCP config, no session
   persistence) for up to 4 DraftCards as JSON. The system prompt inlines, as they are on disk
   when it is built, SKILL.md's "Content rules", "Source text is data" and DraftCard paragraph,
   `checklist.md` and `citation-rules.md` in full, and the FORMAT.md MCQ rules, conventions and
   TOPIC vocabulary;
3. checks every card: DraftCard keys only, `source.quote` 40+ characters and 6+ words, at most
   1000, and **verbatim (whitespace aside) in one of the chunks shown**. Rejected cards are sent
   back once with the reason; a card that fails again is dropped. `source.url` is always the
   ingested url.

Output: `data/authored-v1.jsonl`, rows `{ id, deckSlug, sourceUrl, chunkId, chunkText, card,
authorModel, generatedAt }` in source order then card order, ids `a-0001`, `a-0002`, …. Never run
in CI or tests (the tests pass a fake client and a fake ingest).

### `dc-evals jury` (owner only; spends money)

Each juror (`--jurors provider:model,…`; providers `claude-cli`, `bedrock-converse`, `bedrock`,
`anthropic`) sees one card and the text of the chunk it cites and replies
`{ verdict: "correct" | "defective" | "unsure", category: <QA category> | null, basis: "source" |
"knowledge", reason }`; `basis: "knowledge"` flags a verdict that rests on the juror's own
knowledge rather than the chunk. A failed call or an unparseable reply is an `unsure` vote with
its error code. Default jurors (vendors not under test):

```
bedrock-converse:qwen.qwen3-235b-a22b-2507-v1:0,bedrock-converse:deepseek.v3.2,bedrock-converse:global.moonshotai.kimi-k3
```

Label rule (exact; `jury.label_votes`):

1. Only `correct` and `defective` votes are decisive; `unsure` votes do not count.
2. No decisive vote: excluded (`all_unsure`). Equal `correct` and `defective` votes: excluded
   (`tie`). Otherwise the label is the verdict with more votes.
3. A `defective` label's category is the category most `defective` votes name (nulls ignored);
   a tie goes to the category listed first in `ai_qa.schema.CATEGORIES` (blockers first).
4. Unanimous = every juror cast the label's verdict.
5. For `run` / `score` (`--dataset authored-v1`): a `correct` row is a control (defect null); a
   `defective` row whose category is a seeded class (`incorrect_answer`, `multiple_correct`,
   `answer_leak`, `ambiguous_stem`, `outdated_fact`, `qualifier_mismatch`, `source_unsupported`)
   has that defect; other `defective` rows (`weak_distractor`, `other`, no category) are not
   scorable and are left out, like excluded rows.

Output: `data/authored-v1.labels.jsonl` (one line per authored row with every vote, the label,
`excluded`, `unanimous`, `defect`, `scorable`) and `data/authored-v1.labels.summary.json` (label
counts, exclusions, unanimity rate, and per juror: votes, unsure, errors, knowledge-based votes
and agreement with the majority). The authored-v1 `datasetSha256` is the sha256 of the authored
file's bytes followed by the labels file's bytes, so a new jury run is a new dataset.

**Rationale and limits.** Jury labels are model-generated: no human labels any card. A jury of
three models from other vendors, each grounded in the cited source text, removes the Claude
family's shared blind spots from the labels, but the jurors have their own: a unanimous wrong
label is invisible, the unanimity rate is agreement and not accuracy, and `knowledge`-based votes
depend on each juror's training data (dates, retired limits). Recall on authored-v1 is measured
against the jury, and it is not rollout evidence (the gate stays on `seeded-v3`). Keep the
configuration under test out of the jury's vendors; `compare` warns when a reviewer shares a
vendor with a juror.

**Marketplace note.** Third-party models on Bedrock (Qwen, DeepSeek, Kimi, and any
`bedrock-converse` reviewer) need the owner's one-time Marketplace terms acceptance for each model
and the account's Bedrock allowlisting (model access in the region, and the IAM grant for
`bedrock:InvokeModel` / Converse on the model or inference profile) before `jury` or a
`bedrock-converse` run can call them. Until then those calls fail with an access error and the
vote is recorded as `unsure`.

### Configurations in `run`

`--provider bedrock-converse --model <id>` reviews with a non-Anthropic Bedrock model through the
Converse API (ai-qa Q01; the id must not start with `anthropic.`). `--second-provider` /
`--second-model` (and optionally `--second-scope`) set ai-qa's `AI_QA_SECOND_PROVIDER` /
`AI_QA_SECOND_MODEL` / `AI_QA_SECOND_SCOPE` for the in-process review: a `done` review also goes
to the second reviewer and the findings merge exactly as in the ai-qa handler (Q01 merge policy).
Without `--second-provider` the second reviewer is off even if those variables are exported. The
run header and the report record `secondProvider` / `secondModel` (null when off), the Markdown
names both reviewers, and each item records `secondOpinion: { added, errorCode }` when it is on.
A run with a second reviewer is not the shipping configuration, so the gate refuses it.
`AI_QA_SECOND_PRICE_INPUT_PER_MTOK` / `AI_QA_SECOND_PRICE_OUTPUT_PER_MTOK` price the second call
(unset: estimated at 0).

### `dc-evals compare`

`compare <run files> --name <name>` writes `reports/<date>-compare-<name>.{json,md}` (never
overwriting; `-2`, … when taken): per configuration and dataset, recall with its card-clustered
95% CI, precision, the control FP rate with its CI, precision at a 10% prevalence and the
estimated cost per reviewed card (the run's estimated cost / its items, both reviewers). For
authored-v1 rows it adds the jury caveat from `data/authored-v1.labels.summary.json`
(`--labels-summary` to change): jurors and their vendors, exclusions, unanimity rate, and a
warning when a reviewer shares a juror's vendor. The Markdown states that jury labels are
model-generated (no human labels) and that the jurors come from vendors not under test.

### Recommended runbook (owner only)

```
cd evals
uv run --python 3.12 dc-evals author                      # local Claude CLI; writes data/authored-v1.jsonl
uv run --python 3.12 dc-evals jury                        # 3 jurors x rows; writes the labels + summary
for ds in v3 authored-v1; do                              # 3 configurations x 2 datasets (dry-run each first)
  uv run --python 3.12 dc-evals run --provider bedrock --model anthropic.claude-opus-5 --dataset $ds --out reports/
  uv run --python 3.12 dc-evals run --provider bedrock-converse --model <converse id> --dataset $ds --out reports/
  uv run --python 3.12 dc-evals run --provider bedrock --model anthropic.claude-opus-5 \
      --second-provider bedrock-converse --second-model <converse id> --dataset $ds --out reports/
done
uv run --python 3.12 dc-evals compare reports/<the six run files>.jsonl --name configs
```

Pick a `<converse id>` from a vendor that is not on the jury (for example a Mistral or Meta model),
so the authored-v1 figures stay independent of the labels.

## Gate

All thresholds are constants in one block at the top of `src/dc_evals/score.py`; the report's
`gate.thresholds` echoes them. `score --gate` passes only when all of these hold:

| Condition | Constant | Why |
|---|---|---|
| provider is `bedrock` or `anthropic` | `GATE_PROVIDERS` | `claude-cli` is proxy evidence (`evidenceClass: "proxy"`) and never satisfies the gate by itself |
| provider, model, `promptVersion`, `effort` and `structuredOutputsAtStart` equal the shipping configuration | `SHIPPING_ENV_PATH` | the run must measure what ships: `services/ai-qa/env/prod.env.json` (read through `ai_qa.settings.load_settings`, the mode resolved by `ai_qa.providers.structured_outputs_on`) and the current `ai_qa.prompts.PROMPT_VERSION`; today Bedrock, `anthropic.claude-opus-5`, `qa-v3`, effort `high`, structured outputs off. An `--provider anthropic` run resolves structured outputs to on and measures a different request and repair path |
| dataset is `seeded-v3` and the header's `datasetSha256` equals the committed file's | `GATE_DATASET` | the numbers belong to the committed dataset |
| at least 2 repetitions | `MIN_GATE_REPS` | one repetition of a 15-row class decides its floor by noise; a second one adds precision as far as the two reviews of a card disagree |
| `n` = dataset rows × `reps` | – | a `--limit` or cost-ceiling run is not evidence |
| overall recall ≥ 0.80 and its card-clustered 95% lower bound ≥ 0.75 | `RECALL_GATE`, `RECALL_CI_LOWER_GATE` | contract §12.1; the bound keeps a small or lucky sample from passing (on 113 defective cards reviewed twice it needs recall ≥ 0.8097 when the two repetitions miss different cards and ≥ 0.8319 when they miss the same ones) |
| overall precision ≥ 0.70 | `PRECISION_GATE` | contract §12.1 (at the dataset's 50% prevalence) |
| control false-positive rate ≤ 0.10 and its card-clustered 95% upper bound ≤ 0.15 | `CONTROL_FPR_GATE`, `CONTROL_FPR_CI_UPPER_GATE` | prevalence-independent bound on false alarms (the same 9 of 113 controls flagged in both repetitions, 0.0796, is the most that passes) |
| every class the dataset seeds has ≥ 15 distinct cards and recall ≥ 0.60 on its items pooled over repetitions | `MIN_CLASS_CARDS`, `PER_CLASS_RECALL_FLOOR` | easy classes cannot hide a weak judgment class, and a class is judged on enough cards (a card reviewed twice is one card; Z04 replaced the 30-pooled-item minimum `MIN_CLASS_ITEMS`) |
| every judgment class's why-neutral tier, when the dataset has one, reaches recall ≥ 0.60 on its own | `PER_CLASS_RECALL_FLOOR` | self-evidenced rows cannot carry the rows no why points to ([Label provenance](#label-provenance-of-the-judgment-classes)) |
| unscored (errored/refused/skipped) controls ≤ 2% of controls | `CONTROL_UNSCORED_RATE_GATE` | a failing harness must not look precise |
| every scored item has a verified `servedModel` | – | findings must come from the requested model |

How noisy the per-class floor is (`score.class_floor_pass_probability`, exact binomial, items
treated as independent): a reviewer whose true recall is 0.75 in every class fails a 15-item
floor 5.7% of the time per class, so about a third (33.5%) of single-repetition runs fail at
least one of the seven classes. On 30 pooled items (two repetitions) it fails 2.2% per class, and
the whole run passes all seven floors with probability 0.86 (0.98 at true recall 0.80), while a
weak class at true recall 0.50 still clears the floor only 18% of the time. Repetitions of the
same card are correlated, so these are optimistic; three repetitions (`--reps 3`) tighten them
further. For the control FP rate, a reviewer with true FPR 0.07 exceeds 0.10 on 226 pooled
controls about 5% of the time.

**Unit of analysis (Z04, ai-agent-28).** Point estimates (recall, precision, FP rate, per class
and per tier) pool every repetition. Every 95% interval treats the repetitions of a card as one
cluster (`score.clustered_wilson_ci`): the cluster-robust variance of the pooled rate over cards
gives a design effect, and the Wilson interval uses the effective sample size pooled items /
design effect, kept between the number of distinct cards (the reviews of every card agree) and
the pooled items (they disagree as often as independent reviews would). A rate of 0 or 1 uses the
distinct cards. The class minimum counts distinct cards. The report's `unitOfAnalysis` says so
and gives the card counts; the Markdown summary has a "Unit of analysis" line.

Reported for information: card-clustered 95% Wilson intervals for overall recall, every class's
recall, every tier's recall and the control FP rate, and `precisionAtPrevalence`: the precision the same
reviewer would have at a 10% defect prevalence (`PRODUCTION_PREVALENCE`),
`R·π / (R·π + FPR·(1−π))`.

## Scoring

- A record is **flagged** when it has at least one `blocker` or `major` finding.
- A defective row is a **TP** when it is flagged by a blocker/major finding whose category is in
  its accepted set, else an **FN** (a defective row whose status is not `done` is an FN):

  | Defect | Accepted categories |
  |---|---|
  | `incorrect_answer` | `incorrect_answer` |
  | `multiple_correct` | `multiple_correct` |
  | `answer_leak` | `answer_leak` |
  | `ambiguous_stem` | `ambiguous_stem` |
  | `outdated_fact` | `outdated_fact`, `incorrect_answer` |
  | `qualifier_mismatch` | `qualifier_mismatch`, `ambiguous_stem` |
  | `source_unsupported` | `source_unsupported` |

  Y05 removed `source_unsupported` from the `incorrect_answer` and `outdated_fact` sets: it is a
  major, and only a blocker stops a publish, so it does not catch a wrong answer. Every accepted
  category of a blocker class is itself a blocker. (v1 cards carry no source, so no v1 score
  changes.)
- A flagged control is an **FP**. A control whose status is not `done` is **unscored**: neither
  clean nor an FP, left out of the FP-rate denominator and counted in `unscored.controls`.
- `recall = TP/(TP+FN)` per class and overall, `precision = TP/(TP+FP)`, `f1 = 2PR/(P+R)`,
  `controlFalsePositiveRate = FP/scored controls`; a zero denominator gives `0.0`; ratios are rounded to
  4 decimals. Latency p50/p95 use the nearest-rank method over records with `latencyMs > 0`.
  `errors` counts records per `errorCode`; `estimatedCostUsd` is the sum (6 decimals). The
  Markdown summary also shows how many defective rows were flagged under a wrong category.
- Constants: see [Gate](#gate) and `ACCEPTED_CATEGORIES`.

Report JSON (`v: 2`; X04, Y05 and Z04 added keys, every §12.1 key keeps its meaning): `v, runId,
startedAt, provider, model, promptVersion, dataset, datasetSha256, reps, reviewDate, effort,
structuredOutputs, structuredOutputsAtStart, evidenceClass ("rollout" | "proxy"), n, estimatedCostUsd, perClass{<class>: tp, fn, recall, recallCi95},
overall{tp, fp, fn, recall, precision, f1, controlFalsePositiveRate, recallCi95,
controlFalsePositiveRateCi95, precisionAtPrevalence{prevalence, precision}},
unscored{defective, controls, controlUnscoredRate}, perTier{<tier>: tp, fn, recall, recallCi95},
perRep[{rep, recall, controlFalsePositiveRate}], servedModel{unverified}, structuredItems{on, off},
latencyMs{p50, p95}, errors{<code>: n}, unitOfAnalysis{unit, interval, pointEstimates, classMinimum,
cards{defective, scoredControls, perClass{<class>: n}}}, labels (null unless the dataset has an
adjudication file){source, note, adjudicationFile, perClass{<class>: rows, selfEvidenced, whyNeutral,
humanValid, humanInvalid, unadjudicated}, perEvidence{<class>: {self-evidenced, why-neutral: tp, fn,
recall, recallCi95}}, excludedRows[]}, proxyFidelity (null unless claude-cli){outcomes[], note}, gate{thresholds, expected{datasetSha256, rows, shipping{provider,
model, promptVersion, effort, structuredOutputsAtStart}}, passes, failures[]}`. `perClass` lists the classes the run's dataset seeds (six for v1, seven for v2 and v3).

## Versioning

The report name and body carry the model and `promptVersion`; a prompt change bumps
`ai_qa.prompts.PROMPT_VERSION` and needs a new run. The dataset name and the sha256 of its file
are in every run header; mutation, deck or ledger changes produce a new dataset version.

## Notes on the ai-qa API

- `review_card` propagates exceptions it does not map to a §7.5 error code. The runner records
  such a row as `status: "error"`, `errorCode: "UNEXPECTED"` (the exception class goes to stderr)
  so one broken card does not discard a paid run.
- `ai_qa` logs one JSON line per model call on stdout; set `LOG_LEVEL=warn` to quieten a run.
