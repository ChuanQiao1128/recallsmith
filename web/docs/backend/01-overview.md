1. 我们在解决什么问题
   • 作者侧（Admin Web）：在一个简单、稳定的后台里创建/维护题库（Deck）与卡片（Card），按需“发布”为只读离线包，交付给移动端使用。
   • 用户侧（移动端 App）：只需下载题库包（deck.sqlite + manifest.json），本地完成复习（间隔记忆），即使无网也能用；若题库有新版，提示用户下载，不影响现有复习计划。
   • 系统侧：低成本、易运维、可渐进扩展（本地 SQLite 起步，平滑切 RDS for PostgreSQL；本地磁盘发布起步，平滑切 S3/CloudFront）。

2) 设计目标（面向中级开发者要点）
   • 极简数据模型：只有 decks 与 cards，去掉 draft/version 细粒度耦合；卡片不绑定版本，版本落在“发布包”维度。
   • 发布即版本：发布时将“当前 deck 的卡片快照”烘焙为只读 SQLite 包，版本号仅记录在 deck 层（latest_version）。
   • 低耦合交付：移动端只消费静态包，不依赖在线查询；全局目录 catalog.json 是版本发现源。
   • 一致性与可回滚：发布是可重复的（版本冲突时返回 409），catalog.json 的更新作为最后一步，使客户端看到的是完整产物。
   • 工程化：API Key 鉴权、统一错误、健康检查、结构化日志、分页/检索、输入验证、软删除、时间戳、可观测与迁移策略。

3) 关键取舍
   • JSON vs SQLite（移动端数据）：选择 SQLite。理由：体积小、查询快、支持索引、移动端生态成熟；且与“只读包”理念天然契合。
   • 在线查询 vs 离线包：选离线包。理由：全球访问延迟不稳定、移动端弱网多；离线包 + S3/CloudFront CDN 下发更简单稳健。
   • 本地开发 vs 云：开发用 SQLite + 本地磁盘，生产可切 RDS + S3；通过配置开关实现无侵入切换。
