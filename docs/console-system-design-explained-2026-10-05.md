### 1. 登录

**一句话**：控制台是静态网页，存不了密钥，所以用 Cognito 托管登录，走授权码 + PKCE 流程；每次发请求前检查 token，快过期就先刷新。

**先懂几个词**
| 词 | 大白话 | 类比 |
|---|---|---|
| JWT（access token） | 一段带签名的字符串，写着你是谁、在哪些组、几点过期。服务器验一下签名，就知道它没被改过。控制台的 access token 1 小时过期。 | 带防伪章的临时工牌，背面印着部门和有效期 |
| refresh token | 一张有效期更长（30 天）的凭证。它只用来换新的 access token，不拿去调业务接口。 | 工牌过期后，拿去前台换新牌的登记卡 |
| 授权码 + PKCE | 登录成功后，Cognito 先给一张一次性的"取件码"（code）。网页出发前自己生成一个暗号（verifier），只把暗号的指纹（challenge）告诉 Cognito。换 token 时必须报出原暗号，指纹对得上才给。 | 寄存行李时只登记暗号的指纹；取件要说出原暗号。光偷到取件码，取不走行李 |
| single-flight | 好几个请求同时发现 token 快过期，只派一个去刷新，其他请求等它的结果。 | 一屋子人都渴了，只派一个人去买水 |

**一步一步发生了什么**
1. 编辑点 Sign in。前端生成两个随机串：verifier（暗号）和 state（这次登录的编号）。两者和"登录后要回的页面"一起存进 sessionStorage。前端用 SHA-256 算出 verifier 的指纹 challenge，放进 URL，跳到 Cognito 登录页。
2. 编辑在 Cognito 页面输入邮箱和密码，再输入手机验证器 App 里的 6 位动态码（强制两步验证）。控制台有自己独立的用户池，账号只能由管理员创建，没有自助注册。
3. Cognito 跳回 `/auth/callback`，URL 里带着 code 和 state。它只会跳回事先登记过的地址。前端先核对 state 和自己存的一样，state 和 verifier 用完就删。然后用 fetch 把 code + verifier 发给 Cognito，换回 access token、id token 和 refresh token，存进 sessionStorage。
4. 前端把编辑送回登录前的页面。这个地址在存入和取出时各检查一次，只接受本站内的路径，防止登录后被带到外部网站。
5. 之后所有 API 请求共用一个 axios 实例，超时 15 秒。每次发请求前先看 token：剩不到 60 秒或已经过期，就先用 refresh token 换新的，再把请求发出去。没有后台定时器。
   - 例子：页面一打开同时发 3 个请求，token 只剩 40 秒。这 3 个请求共用一次刷新，等它回来再一起发出。
6. 刷新失败，这个请求就不发了。服务器回 401 也一样处理：清掉 token，跳回登录页。很多请求同时失败，也只跳一次。数据库全程不参与：密码由 Cognito 保管，我们不存。

**为什么这样设计**
- 问题是网页代码谁都能下载来看，藏不住客户端密钥，所以控制台是"公开客户端"，靠 PKCE 保护：code 在 URL 里被人截走也没用，因为换 token 还要 verifier。
  - 取舍：token 放在 sessionStorage，页面里的 JS 能读到。页面一旦混进恶意脚本就有风险，这个风险靠"只允许运行本站脚本"的严格安全策略来压低。另外，登出不会撤销 refresh token。
- 问题是 access token 1 小时就过期，编辑写到一半被踢出去会丢内容，所以每次发请求前检查，提前 60 秒刷新。60 秒是算出来的：一个请求最长 15 秒；token 存储模块（tokenStore）把剩不到 30 秒的 token 当成已过期；60 秒两边都盖住。
  - 取舍：刷新只在发请求前发生，不是定时器。快到期后的第一个请求要多等一次刷新。
- 问题是页面一打开会同时发好几个请求，各自刷新就会向 Cognito 重复发好几次刷新请求。现在没开 refresh token 轮换，重复刷新不会互相作废；但如果以后开了轮换，后到的请求会拿着已经作废的 refresh token 刷新失败，把用户登出。所以用 single-flight 只刷新一次，两种情况都防住。

**面试官可能追问**
1. **问：PKCE 到底防什么？**
   答：防 code 被截走后被别人换成 token。换 token 必须带原始 verifier，而 verifier 一直留在这个浏览器里，只在最后换 token 时才发给 Cognito。
2. **问：token 放在 sessionStorage 安全吗？**
   答：不是绝对安全，JS 能读到它，我们靠严格的安全策略只允许本站脚本运行来降低风险。我也会主动说明：登出时不会撤销 refresh token，这是已知的边界。

**English**
"It's a static SPA, so it signs in with the authorization code flow plus PKCE. Before each request it refreshes the token if less than a minute is left, and concurrent requests share one refresh."

### 2. 权限：三层把关

**一句话**：前端只负责按角色隐藏按钮，真正的把关在网关和后端：网关先验 token，后端再验角色和卡组权限。

**先懂几个词**
| 词 | 大白话 | 类比 |
|---|---|---|
| Cognito 组（`cognito:groups`） | token 里的一个字段，列出这个账号属于哪些组。控制台只有两个组：`super_admin` 管全站，`editor` 只能碰被授权的卡组。 | 工牌上印的职位 |
| 受众（audience） | token 里写着"这张票是发给哪个客户端的"。控制台、AI agent、手机 App 各有自己的客户端。 | 电影票上印着几号厅，走错厅不让进 |
| JWT authorizer | API Gateway 自带的检票员。请求到达 Lambda 之前，它先验签名、过期时间、签发方和受众。 | 大楼门口的闸机 |
| 401 和 403 | 401：我不认这张票（无效、过期、受众不对），请重新登录。403：票是真的，但你没有这个权限。 | 401 是保安说"请出示有效工牌"；403 是"工牌没问题，但这层你不能进" |

**一步一步发生了什么**
1. 前端：把 token 中间那段解码出来，读 `cognito:groups`。它不验签名，所以结果只用来决定显示什么。不是 super_admin，就隐藏新建卡组、发布、删除、回滚、Webhooks、Admin 这些入口。**隐藏不等于禁止。**
2. 网关：请求带着 `Authorization: Bearer <token>` 到 API Gateway。控制台和手机端要登录的路由，每条挂一个检票员，一共 3 个：console 只认控制台网页的 client；agent 认控制台 client 和本地 agent 的 client，只挂在那 6 条 agent 路由上；mobile 只认手机 App 的 client。健康检查、CORS 预检、RevenueCat 回调、内部 HMAC 回调和两条匿名公开接口不挂检票员，靠各自的密钥、签名或限流保护。签名不对、过期或受众不对，网关直接回 401，Lambda 根本不会被唤醒。
3. core-vpc（后端 Lambda）先看 token 是不是控制台用户池、控制台 client 签发的。是，才承认里面的管理员组。不是，就算 token 里写着 editor 也不算：身份保留，角色清空，需要管理员的路由回 403。
4. 每条路由再调用对应的检查：`RequireAdmin`（editor 或 super_admin 都行）、`RequireSuperAdmin`，或者卡组级的 `RequireDeckRead` / `RequireDeckWrite`。
5. 卡组级检查查 `admin_deck_permissions` 表。每行记录一个账号（Cognito sub，也就是账号的唯一 ID）对一个卡组的 `can_read` / `can_write`，(admin_sub, deck_id) 唯一，数据库默认值是可读、不可写。super_admin 不查这张表，直接放行。
   - 例子：editor 小王只有卡组 7 的读权限。他打开卡组列表，只看得到卡组 7，因为列表查询直接和权限表关联过滤。他保存卡组 7 里的一张卡，后端先由卡片 id 查出它属于卡组 7，再查 `can_write`，没有，回 403。
6. AI agent 的 token：它签给本地 agent 用的 client，带着 owner 自己的组，所以要额外收紧。它只能访问 6 条路由：列卡组、找相似卡、提交草稿，加本地 runner 的心跳、领任务、交结果。打到其余控制台路由时，网关的 console 检票员不认它的受众，直接回 401；万一漏进来，core-vpc 里的同一份名单再回 403 `AGENT_CLIENT_FORBIDDEN`。

**为什么这样设计**
- 问题是前端代码在用户手里，任何人都能绕过页面直接调 API，所以前端只管体验，真正的规则放在服务端。
  - 取舍：同一条规则前后端各写一份，就可能不一致。现在就有一处：发布按钮前端只给 super_admin 看，但后端只要求卡组写权限，有写权限的 editor 直接调 API 也能发布。
- 问题是坏 token 不该占用后端，所以签名、过期、受众这些通用检查交给网关，被拦下的请求不会唤醒 Lambda。网关不懂"谁能写卡组 7"这种业务规则，所以卡组级检查留给 Lambda 查数据库。
  - 取舍：每次卡组级检查都多一次数据库查询。
- 问题是 agent 的 token 存在本机磁盘上，agent 自己的工具也能读到，而它带着 owner 的组，所以网关和 core-vpc 各放一份 6 条路由的名单。CI 里有脚本核对：网关上的 agent 路由必须正好是 agent 实际调用的那几条，而且每条都在 core-vpc 的白名单里；白名单多出来的条目只报警告。
  - 取舍：加一条 agent 路由要同时改两处。

**面试官可能追问**
1. **问：前端已经隐藏了按钮，后端为什么还要查？**
   答：前端只是方便使用，任何人都能用 curl 直接调 API，真正的规则必须在服务端。我也会主动说一处不一致：发布按钮只对 super_admin 显示，但后端只要求卡组写权限。
2. **问：agent 的 token 带着 owner 的组，怎么防止它乱调接口？**
   答：它只能访问 6 条路由，其余控制台路由大多在网关就因为受众不对被 401 拒掉。漏进来的请求，再由 core-vpc 里的同一份名单回 403。

**English**
"Authorization happens in layers: the UI hides buttons, API Gateway validates the JWT audience, and the Lambda reads the role from the token's Cognito groups and checks per-deck read and write permissions in PostgreSQL. Hiding a button is not a permission check; the server enforces every rule."

### 3. 编辑卡组和卡片

**一句话**：两个人同时改同一张卡时，后保存的人不会悄悄覆盖前一个人，而是收到冲突提示。这叫乐观并发：用版本号判断，不加锁。

**先懂几个词**
| 词 | 大白话 | 类比 |
|---|---|---|
| 乐观并发 | 打开时不锁，保存的那一刻才检查"我读到的还是不是最新的"。不是最新，就拒绝这次保存。 | 共享文档：改之前不占座，交稿时看一眼版本号有没有变 |
| 版本号（`version` / `expectedVersion`） | 每张卡一个计数器，从 1 开始，每保存成功一次加 1。`expectedVersion` 是"我打开时看到的版本"。 | 文件名后面的 v3、v4 |
| 409 Conflict | HTTP 状态码，意思是"你的请求和服务器现在的状态冲突了"。 | 你去改座位，柜台说"这个座位刚被别人改过了" |
| 软删除 | 不真删这一行，只把 `is_deleted` 标成 1。数据还在，查询时把它过滤掉。 | 扔进回收站，不是粉碎 |

**一步一步发生了什么**（例子：编辑 A 和 B 同时打开第 9 张卡）
1. A 和 B 打开编辑页。页面用 React Query（前端的请求缓存库）读到同一张卡，`version` 都是 3。`stable_uid`（手机端记学习进度用的稳定 ID）在页面上只读。两人一开始改，"未保存修改"守卫就打开：站内跳转会弹确认框，刷新或关标签页会触发浏览器的"离开此网站？"提示。
2. A 先点保存。前端发一个 PUT，带上 `expectedVersion = 3`。后端先由卡片 id 查出它属于哪个卡组，检查写权限。然后执行一条更新：`where id = 9 and version = 3`，同时把 `version` 改成 4。更新到 1 行，成功。前端让"这个卡组的卡片列表"和"这张卡"两份缓存失效，下次读到的就是新数据。
3. B 后点保存，也带着 expectedVersion = 3。数据库里已经是 4，条件不成立，一行都没更新。后端再按 id 查一次这一行：行还在（软删除的卡也算还在），就回 409 VERSION_CONFLICT；只有这一行在数据库里根本查不到，才回 404。
4. B 的页面收到 409，跳过缓存重新读一次这张卡，只拿回最新的版本号 4，B 输入的内容原样保留。页面出现 "Retry with latest version"。B 点它，就带着版本 4 再保存一次，覆盖 A 的修改。这是明确的后写者胜：B 知道自己在覆盖。如果重新读也失败，就不给这个按钮，提示刷新页面。
5. 如果改的人是 editor：改卡组时，定价层级、上架状态、排序、slug（卡组的英文短名）这些字段会被后端忽略，响应里列出被忽略的字段。改卡时不能改 `stable_uid`，也不能把卡移到别的卡组。删除卡组和删除卡片都是软删除，只有 super_admin 能做。
6. 数据库里存的是：
   - `cards`：(deck_id, stable_uid) 唯一，(deck_id, order_in_deck) 唯一，`version` 就是这把乐观锁。
   - `decks`：slug 唯一，`is_deleted` 做软删除，`live_build_id` 指向线上正在用的构建。注意：`decks.version` 只是普通字段，不是锁；只有卡片有乐观锁。

**为什么这样设计**
- 问题是两个人同时编辑时，后保存的人会悄悄覆盖前一个人，所以每次保存都带版本号，用一条带条件的 UPDATE 判断。
  - 取舍：系统不自动合并两份内容，冲突时由用户自己决定；"Retry" 就是明确覆盖。
- 问题是编辑可能开着页面很久才保存，一打开就锁住这一行会挡住别人，还得处理锁什么时候释放，所以只在保存那一刻比版本号，不占任何锁。
  - 取舍：只保护了单卡编辑。Markdown 批量导入不检查版本，可能覆盖同时进行的单卡编辑，这是已知、接受的取舍。
- 问题是手机端按 `stable_uid` 记学习进度，改了它进度就对不上，所以编辑页把它设成只读，后端也不让 editor 改。slug 同理：它是线上构建文件和手机进度的键，卡组发布过（或正在发布）之后，连 super_admin 也改不了，返回 409 `SLUG_LOCKED`。
  - 取舍：`stable_uid` 只在应用层保护，数据库没有强制，super_admin 直接调 API 仍然能改。

**面试官可能追问**
1. **问：为什么不用悲观锁，打开时就把这一行锁住？**
   答：编辑可能开着页面很久，锁一直占着会挡住其他人，还要处理锁超时。乐观并发只在保存那一刻比一下版本号，适合"读很久、写一下"的编辑场景。
2. **问：B 点 Retry 不还是覆盖了 A 吗？那和没有版本号有什么区别？**
   答：区别在于 B 知不知情。没有版本号时，B 不知道 A 改过就把它覆盖了；现在 B 先收到冲突提示，再自己决定覆盖，这是明确的后写者胜，不是悄悄覆盖。

**English**
"Card edits use optimistic concurrency: each save carries the version it read, and a stale version gets a 409 instead of silently overwriting someone. The editor keeps their changes and can choose to retry on top of the latest version."

### 4. 批量导入 Markdown

**一句话**：导入按 stable_uid 对账，先预览再执行，只新增和更新、从不删除；中途失败重试也不会重复写。

**先懂几个词**
| 词 | 大白话 | 类比 |
|---|---|---|
| stable_uid | 每张卡固定不变的名字，比如 `cs-async-001`。题目改了，它也不变。手机端按它记学习进度。 | 学号：换座位、改名字，学号都不变 |
| upsert | 按一个键去找：找到就更新，找不到就插入。一条 SQL 就能做完。 | 通讯录按手机号存人：号码已有就改备注，没有就新建 |
| 事务（transaction） | 一组写入要么全部成功，要么全部撤销，不会只写一半。 | 银行转账：扣款和入账必须一起成功 |
| 幂等（idempotent） | 同一个请求发一次和发十次，结果一样。 | 电梯按钮按五下，电梯也只来一次 |

**一步一步发生了什么**
1. 编辑在导入页粘贴或上传 Markdown。每张卡以 `## cs-async-001 | d2` 这样的一行开头，写的是 uid 和难度，下面跟着 `Q:` 和 `A:`。
2. 前端解析文件，每次都从服务器重新读一遍这个卡组现有的卡，再按 stable_uid 一张张对上。结果分四类：新建（预览读到的未删除卡里没有这个 uid）、更新（有，但内容不同）、不变（内容完全一样）、冲突（比如同一个 uid 在文件里出现两次，或者卡片本身不合格）。只要有冲突，导入按钮就点不了。预览读不到已删除的卡，所以撞上已删除卡的 uid 也会显示为新建，要到执行时才由服务器整批返回 409 SOFT_DELETED_UID。
3. 点导入后，前端只发"新建"和"更新"两类。按"每批最多 500 张、最多 900,000 字符"切批，一批一个请求。遇到超时、网络错误、429 或 5xx，就分别等 1 秒、2 秒、4 秒再试。等待时间逐次变长，这叫退避。
4. 后端先查卡组写权限，然后每批开一个事务。先锁住这个卡组的那一行，别的导入只能排队。再逐张 upsert，键是 (deck_id, stable_uid)。SQL 里有个条件：新内容和旧内容不同才更新。所以内容没变就不写，版本号也不加。
5. 如果某个 uid 属于一张已删除的卡（SOFT_DELETED_UID），或者某个排序号被这一批之外的一张未删除的卡占着（ORDER_CONFLICT），整批返回 409，一张都不写。如果占着排序号的是已删除的卡，服务器会把它挪到最后，不算冲突。
6. 卡片写进 cards 表。每一批请求结束后，各在自动化账本记一条 bulk_import：成功记，失败也记。只有通过了卡组权限检查、又以 400、409 或 503 失败的批次，才会记这条失败，并产生 import.failed 的 webhook 事件；500 或权限被拒都不会。

举个例子：第 2 批请求超时了，其实服务器已经写进去了。前端 1 秒后重发同一批。服务器发现每张卡都"内容没变"，全部返回 unchanged，一张也不会多写。

**为什么这样设计**
- 问题是手机端按 stable_uid 记学习进度。所以对账只认 stable_uid，不认题目文字，也不认数据库 id。导入也从不删卡，因为删了卡，用户的进度就对不上了。代价是导入删不掉多余的卡，要删得单独操作，而且只有 super_admin 能删。
- 问题是请求超时的时候，前端不知道上一批到底写没写进去。所以把写入做成幂等，可以放心重发，重发的结果只会是"不变"。
- 问题是 API 请求体有 1 MiB 上限，后端一次最多收 500 张。所以前端切批，每批一个事务，坏数据不会只写一半。代价是批与批之间不在一个事务里，可能前几批成功、后面某一批失败。

**面试官可能追问**
1. **导到一半失败了怎么办？** 失败的那批整批回滚，结果页会把它的卡都列出来，其他批照常继续。重新预览一次，已经写进去的卡会显示"不变"，再导一次就只补剩下的。
2. **导入会不会覆盖别人刚改的卡？** 会，这是已知、已接受的取舍：导入按文件内容覆盖，不检查版本号。只有单张卡的编辑页用版本号防止覆盖。

**English**
"Markdown import is idempotent: it's keyed by a stable ID, previewed as create, update, unchanged or conflict, never deletes, and a retried batch simply comes back unchanged. Each batch is one transaction, so a failed batch writes nothing."

### 5. 审核 AI 草稿

**一句话**：AI 只能提交草稿。生产上自动化是 dry_run，所以每张草稿都由人接受、修改后接受或拒绝；接受时，写卡、关草稿、记审核事件在同一个事务里完成。

**先懂几个词**
| 词 | 大白话 | 类比 |
|---|---|---|
| MCP | 让 AI 调用外部工具的一套标准接口。本地的 AI agent 通过它调我们的 API。 | 给 AI 定的"插座标准" |
| dry_run | 自动化照常做判断，但只记下"本来会怎么做"，不真的动手。 | 实习生写好处理意见，签字的还是主管 |
| 行锁（SELECT ... FOR UPDATE） | 在事务里先锁住这一行。别的事务想改同一行，要等前一个提交。 | 会议室门口挂上"使用中" |
| 只追加（append-only） | 只能插入新行。数据库触发器禁止修改和删除。 | 账本只能往后写，写错了也只能再记一笔更正 |

**一步一步发生了什么**
1. 本地 AI agent 通过 MCP 工具调用提交草稿的接口。每张草稿带一个 client_draft_key，同一个卡组里不能重复。agent 重发同一张，只会拿回原来那条草稿的 id。服务器还会在同卡组里找出最多 3 张相似的已有卡附上，帮审核的人发现重复。
2. 草稿存进 ai_drafts 表，状态是 pending，同时写一条 submitted 审核事件。这时它还不是正式的卡，学习者看不到。
3. 编辑打开 /review 审核队列，有三个选择：直接接受、修改后接受、选一个原因拒绝（比如 incorrect、duplicate、off_topic）。前端同时计时，只算页面可见的时间，单张最多算 30 分钟。
4. 点接受后，后端先查卡组写权限，再开一个事务：锁住这条草稿，确认它还是 pending，插入一张正式的卡，把草稿标成 accepted，最后写一条审核事件。插卡前会确认这个 stable_uid 在卡组里没被用过，用过就返回 409。修改后接受的，事件里还存改前和改后的内容。
5. 举例：编辑 A 和 B 同时接受第 9 号草稿。A 先拿到锁，写完提交。B 等到锁以后，发现状态已经是 accepted，收到 409 DRAFT_NOT_PENDING。所以一张草稿只会变成一张卡。
6. 拒绝也一样：锁住草稿，标成 rejected，写一条带原因的事件。事务提交后，再把审核用时记进自动化账本。这一步尽力而为，失败了也不影响审核结果。

**为什么这样设计**
- 问题是 AI 会写错，写错的卡会直接到学习者手上。代码里有 live 模式的自动接受，但必须先通过评测门槛，现在没开，生产是 dry_run。所以每张都由人拍板。代价是要花人工时间，所以审核用时要记进账本，算清楚自动化到底省了多少。
- 问题是"插入卡片"和"关闭草稿"如果分两步做，中间一崩，就会出现卡已经有了、草稿却还开着，可能被再接受一次。所以两步放进一个事务，再加行锁，保证草稿只离开 pending 一次。代价是要排队：接受时除了锁草稿，还会锁卡组那一行，所以同一个卡组里的接受和导入都得一个一个来，不只是同一条草稿上的请求。好在量很小。
- 问题是 agent 的 token 存在本地磁盘上，它自己的工具可能读到。所以这个 token 只开了 6 条路由，接受和拒绝不在里面。它去调接受，多半在网关就被 401 拒掉；漏进后端的，也会被白名单挡成 403。代价是多一道人工环节，换来 AI 不能自己批准自己。

**面试官可能追问**
1. **以后想让 AI 自动接受，要改什么？** 代码里已经有 live 模式的自动接受，用的是同一个接受事务。要打开它，下面几条要同时满足：AUTOMATION_MODE 设成 live；最新一次评测门槛通过且没被撤销；AI_QA_ENABLED 打开（生产上是 0）。草稿还要先过 AI 质检（没有 blocker 和 major），质检用的模型和草稿的作者配置都要和门槛测的一致。任何一条不满足，草稿就转给人审。门槛没过时，设成 live 也按 dry_run 跑；撤销门槛就等于一键关掉。
2. **agent 把同一批草稿提交了两次，会出两份吗？** 不会。(deck_id, client_draft_key) 是唯一键，重复的那条直接返回已有草稿的 id，不会多建。

**English**
"The AI agent can only submit drafts. In production, where automation runs in dry-run mode, a person accepts, edits or rejects each one, and accepting inserts the card, closes the draft and logs a review event in one transaction."

### 6. 发布前检查

**一句话**：发布前可以先打开预览页，在浏览器里用模仿手机端的规则检查一遍（可选，不拦发布）；真正拦发布的是服务器上的选择题格式门禁。AI 质检门禁也在服务器上，但生产上是关着的。

**先懂几个词**
| 词 | 大白话 | 类比 |
|---|---|---|
| 门禁（gate） | 发布任务进队列之前，服务器跑的一道检查。不合格就拒绝这次发布。 | 登机前的安检口 |
| 内容哈希 | 把一张卡的内容算成一串固定长度的指纹（SHA-256）。内容改一个字，指纹就变。 | 文件的校验码 |
| 部分唯一索引（partial unique index） | 只对满足条件的行生效的唯一约束。这里的意思是：每个卡组最多一条"排队中或运行中"的质检。 | 一个班同一时间只发一张出门条，人回来了才能发下一张 |
| HMAC 签名 | 用双方共享的密钥给消息算一个签名。收方重算一遍，对得上才相信消息没被伪造。 | 只有两边知道的暗号 |

**一步一步发生了什么**
1. （可选）编辑打开预览页。前端用已经缓存的卡组和卡片，在浏览器里拼一个近似的 deck.json，也就是手机端下载的卡组文件。已删除的卡会去掉，其余按排序号排好。版本号固定显示 0.0.0，因为它不是真正的构建。
2. 前端用模仿手机端的规则检查。缺 slug（卡组的网址名）、uid 重复、排序号重复算错误；题目为空、难度不在 1 到 3 算警告。没有错误时，这份 JSON 可以复制或下载。这一步不写任何数据，也不在发布按钮的流程里。
3. super_admin 在卡组列表点发布（前端只给 super_admin 显示发布按钮，后端只要求卡组写权限）。后端查完写权限、读出卡组和卡片后，按卡片顺序跑选择题（MCQ）格式门禁。规则包括：选项要 3 到 6 个，至少一个正确但不能全对，错误选项要写为什么错，解析不能为空，难度要在 1 到 3。碰到第一张不合格的卡，就返回 400 MCQ_PUBLISH_GATE，带上那张卡的 stable_uid。比如第 12 张只有 2 个选项，发布直接被拦下，这时任务不会创建，队列里也没有消息。
4. 接着是 AI 质检门禁。只有 AI_QA_ENABLED 和 AI_QA_REQUIRED 两个开关都打开才会拦。生产上两个都是 0，所以它直接放行，连数据库都不查。手动开始一次质检，也会收到 503 AI_QA_DISABLED。
5. 如果打开了：门禁只看线上构建（decks.live_build_id 对应的那次发布）之后新增或改过的卡；卡组还没有线上构建时，看全部卡。回滚之后，线上构建比最近一次发布更早，要看的卡就更多。每张卡都要在当前的内容哈希下审过，而且不能有未处理的 blocker（最严重的一级）问题，否则返回 409。major 和 minor 不拦。
6. 质检本身这样跑：每 5 张卡打成一块，发到 AWS 的消息队列 SQS。数据库所在的私有网络（VPC）不能出外网，所以由 VPC 外的 Python Lambda 去调模型，再通过带 HMAC 签名的回调把结果写回 ai_qa_runs、ai_qa_items、ai_qa_findings 三张表。

**为什么这样设计**
- 问题是 worker 会把选择题数据原样写进 deck.json，坏数据会直接到手机上。同一套选择题校验在每次写入（保存单卡、导入、提交草稿）时已经跑过。发布门禁是第二道：排队之前再查一遍库里已存的卡，拦住按现在规则已经不合格的旧数据，比如规则收紧前存进去、只有 2 个选项的卡。浏览器预览只是方便，任何人都能绕过前端直接调 API。代价是预览和服务器查的根本不是同一套东西：预览只查文件形状（slug、uid、排序号、题目、难度），完全不查选择题格式。它叫"近似"，是因为真正的 deck.json 由 worker 生成，版本号是构建 id，浏览器里拼的只是仿制品。所以预览通过也不保证能发布。
- 问题是 AI 质检要调模型，要花钱，也要等。所以它由两个开关控制，生产上关着。代价是今天真正拦发布的只有格式检查，内容质量要靠人来把关。
- 问题是卡片一改，旧的质检结果就不算数了。所以按内容哈希记录审过的是哪个版本，改了就要重审。部分唯一索引再保证一个卡组同时只有一个质检在跑，不会重复调用模型。

**面试官可能追问**
1. **预览页查出错误，能阻止发布吗？** 不能。它只在浏览器里跑，不写数据，也不在发布流程里；真正拦发布的是服务器上的选择题格式门禁。
2. **（打开质检以后）两个人同时点"开始质检"会怎样？** 部分唯一索引只允许每个卡组有一条排队中或运行中的质检。后到的那次插入会撞上索引，返回 409 AI_QA_RUN_IN_PROGRESS，不会同时跑两份。

**English**
"Before publishing, an editor can preview the export in the browser and check it against rules modelled on the app's. On the server, an MCQ format gate blocks bad decks, and an AI QA gate exists but is switched off in production."

### 7. 发布（异步）

**一句话**：点发布只写一条任务、发一条队列消息；worker 生成一个不会再改的卡组文件，再用一条 SQL 把"线上版本"指针切过去，最后重建清单。

**先懂几个词**
| 词 | 大白话 | 类比 |
|---|---|---|
| SQS 队列 + worker | SQS 是 AWS 的消息队列，像一个放"待办纸条"的信箱。worker 是另一个 Lambda，专门从信箱里取纸条干活。遇到系统错误（比如数据库或 S3 临时出错）的纸条，大约一小时后会被重新投递；第 3 次还失败，任务标成 FAILED，纸条挪进"死信队列"留着查。业务错误（比如卡组里没有卡片）直接标成 FAILED，不再重试。 | 前台接单开小票，后厨照着小票做菜 |
| 条件 UPDATE（抢任务） | `UPDATE ... WHERE 状态 = 'PENDING'`（或者是很久没进展的 PROCESSING），然后看改到了几行。改到 1 行，就是自己抢到了；改到 0 行，就是没抢到：可能别人正在做，也可能任务已经结束。 | 两个人抢一个车位，先把车开进去的算 |
| 部分唯一索引 | 只对满足条件的行做唯一检查。这里只看 PENDING / PROCESSING 的行：每个卡组最多一行。成功和失败的旧行可以有很多。 | 一个窗口同一时间只能有一个人在办，办完的人不算 |
| 不可变构建 + 指针 + 清单 | 每次发布写一个新目录，名字不重复，写完不再改。`decks.live_build_id` 是指针，记"线上用哪一个"。清单 `manifest.json` 是手机先读的目录，告诉它每个卡组现在用哪个构建。 | 每一版书都留在书架上，目录卡上写着"现在借第几版" |

**一步一步发生了什么**
例子：编辑给卡组 `aws-saa` 点了 Publish。
1. **前端**：弹出确认框，里面能看到质检状态。确认后发请求，几乎马上拿到一个 jobId，不等构建完成。super_admin 打开卡组列表页后，页面轮询整个发布任务列表：有任务在跑时先 2 秒查一次，再逐步放慢到每 10 秒；空闲时更慢；标签页隐藏就暂停。
2. **core-vpc 检查**：先查卡组写权限，再过选择题格式门禁（AI 质检门禁在生产上是关着的）。如果这个卡组已经有进行中的任务、并且 15 分钟内还有更新，就直接返回原来的 jobId。所以狂点不会多建任务。注意：前端只给 super_admin 显示发布按钮，后端却只要求卡组写权限，这是已知的不一致。
3. **core-vpc 收单**：写一行 PENDING 任务，同时生成这次的 buildId，例如 `20261005T093000Z-a1b2c3d4`（UTC 时间加 8 位随机字符）。然后发一条 SQS 消息。如果发送失败，立刻把这一行标成 FAILED，不留没人处理的孤儿任务。
4. **worker 抢任务**：收到消息后，用条件 UPDATE 把任务改成 PROCESSING：只有 PENDING，或者很久没进展的 PROCESSING（重投递时超过 11 分钟，任何时候超过 15 分钟）才能被抢。同时到达的重复消息只有一个能改到 1 行；前一个 worker 崩溃后，重投递的消息可以接管它留下的 PROCESSING 任务。改到 0 行时，如果任务已经是 SUCCESS 或 FAILED，就确认后丢掉这条消息；如果还在别人手里，就让 SQS 稍后再投。FAILED 是终态，不会再被抢。
5. **worker 构建和切换**：把 `deck.json` 写到 `builds/{buildId}/`，缓存头设为一年、不可变。然后用一条 SQL 同时做三件事：任务标 SUCCESS、`live_build_id` 指向新的 buildId、更新卡片总数。同一个事务里还会写入 webhook 待投递行。
6. **清单**：重建 `manifest.json`，缓存 60 秒。手机通过 CDN（离用户近的缓存服务器）读它，用 ETag（文件内容的指纹）判断它有没有变。

**为什么这样设计**
- 问题是构建耗时不受控：大卡组要生成 `deck.json`、分块包和增量补丁。worker 最长能跑 615 秒，而 API Gateway 30 秒就超时。所以拆成"API 快速收单 + worker 慢慢做"。取舍是多了队列、任务表和前端轮询。要说实话：实测最慢一次只有 4.6 秒，异步是为上限留余量，不是现在已经很慢。顺带拿到了 SQS 对系统错误的重试（一条消息最多收 3 次，之后进死信队列）。
- 问题是用户会狂点、消息会重复投递，所以有三道防线：15 分钟内复用 jobId；部分唯一索引限制每个卡组只有一个进行中的任务；worker 用条件 UPDATE，只让一个抢到。取舍是：一个超过 15 分钟没动静的卡住任务，会让下一次发布被索引挡住，返回 409 `PUBLISH_IN_PROGRESS`。卡在 PENDING 的可以马上用 reaper 清掉；卡在 PROCESSING 的要等 30 分钟没进展后 reaper 才会清，15 到 30 分钟之间只能等（见第 8 节）。
- 问题是 CDN 会缓存旧文件，覆盖同名文件可能让手机读到新旧混杂的内容。所以构建文件从不覆盖，切换只改一个指针，而且一条 SQL 原子完成。取舍是"不可变"靠约定（每次新 buildId 加缓存头），不是 S3 本身禁止覆盖。

**面试官可能追问**
1. **SQS 重复投递，会不会发布两次？** 不会。条件 UPDATE 只让一个 worker 抢到；任务已经是 SUCCESS 或 FAILED 时，再来的消息会被确认后丢掉。
2. **写库成功、发 SQS 失败怎么办？** 立刻把这一行标成 FAILED，接口报错。编辑再点一次，就会新建一个任务，不会留下永远等不到 worker 的孤儿任务。

**English**
"Publishing is asynchronous: the API writes a pending job and queues it in SQS, and a worker claims it with a conditional update, writes an immutable build to S3, flips the live-build pointer in one SQL statement and rebuilds the manifest. A partial unique index allows only one active publish per deck."

### 8. 回滚和清理

**一句话**：回滚不需要重新构建，只要把指针移回以前某个成功的构建；移动指针和写审计在同一个事务里完成。

**先懂几个词**
| 词 | 大白话 | 类比 |
|---|---|---|
| 回滚（移指针） | 不重新构建，只把 `decks.live_build_id` 改回以前某个成功的 buildId。旧文件一直在 S3 上，直接拿来用。 | 换台：节目都还在播，只是换个频道 |
| 事务 | 几条写操作打包在一起：要么全部生效，要么全部不算。 | 转账时扣款和入账必须一起发生 |
| 审计表 `admin_audit` | 只能追加的操作日志：谁、做了什么、对什么、改前和改后。数据库触发器禁止改和删。 | 飞机的黑匣子 |
| reaper（清理卡住的任务） | 把所有卡组里太久没进展的 PENDING / PROCESSING 任务标成 FAILED，让这些卡组能再次发布。 | 关门前清掉一直被占着的储物柜 |

**一步一步发生了什么**
例子：9 点发布的构建 B 里有一道错题，想退回 8 点的构建 A。
1. **前端**：只有 super_admin 能看到卡组编辑页的构建面板。点 "Show builds" 才去加载，按时间从新到旧，列出这个卡组最近 50 个成功的构建。线上那个标着 Live，其他每一行都有 "Roll back to this build" 按钮。
2. **前端确认**：点 A 那一行的回滚按钮，弹窗要求手动输入卡组的 slug（比如 `aws-saa`），输对了才能确认，防止手滑。这个检查只在前端做。
3. **后端检查**：接口只有 super_admin 能调。A 必须是这个卡组的 SUCCESS 构建，否则返回 400。
4. **后端写库**：在一个事务里做两件事：把 `live_build_id` 从 B 改成 A；写一条审计 `deck.rollback`，改前是 B，改后是 A。任何一步失败，两件都不生效。提交后重建清单。清单在 CDN 上最多缓存 60 秒，所以最多大约一分钟后，手机检查清单时就会拿到 A。B 还留在列表里，以后可以再切回去。
5. **清理卡住的任务**：卡组编辑页构建面板的底部有一个 "Maintenance (all decks)" 区域，里面的 "Reap stuck jobs" 按钮要 super_admin 手动点。它不只清当前卡组：所有卡组里创建超过 10 分钟还是 PENDING、或者 30 分钟没进展的 PROCESSING 任务，都会被标成 FAILED。后端在同一个事务里写审计 `publish.reap`。一个都没清到也会记一条，因为点按钮本身就是一次管理操作。被清掉的任务是终态：worker 不会再抢它，原来的 worker 就算后来跑完也切不了指针。要恢复，只能重新发布。

**为什么这样设计**
- 问题是发布出错要快速止血。所以回滚只移指针、不重新构建：几乎立刻完成，也不会出现"重建出来的和当初不一样"。CDN 也不用刷新缓存，因为文件名从没被复用。取舍是依赖旧构建一直留在 S3 上；而"不可变"靠约定，不是 S3 禁止覆盖。
- 问题是"谁、什么时候把线上切到了哪一版"必须查得到。所以改指针和写审计放在同一个事务里：有改动就一定有记录。取舍是清单重建在提交之后，不在事务里。如果重建失败，指针已经动了，要再点面板上的 "Rebuild manifest" 补一次。
- 问题是 worker 崩溃或一直没取到消息时，会留下卡在 PENDING / PROCESSING 的行，部分唯一索引会因此挡住这个卡组的下一次发布。所以要有 reaper。取舍是现在只能手动点，没有定时任务。

**面试官可能追问**
1. **回滚之后再发布会怎样？** 正常发布。新构建成功时，同一条 SQL 会把指针移到新的 buildId，回滚不会锁住卡组。
2. **审计覆盖了所有操作吗？** 没有。回滚和清理写审计，但发布、删除卡组、删除卡片不写；发布记在 `deck_publishes`，里面有谁发的、状态和时间。控制台也没有查看审计日志的页面。

**English**
"Because builds are never overwritten, a rollback just moves the pointer back to an earlier successful build, in one transaction with an audit record. Stuck jobs are marked failed by a reaper that a super admin currently runs by hand."

### 9. 发布后：学习者反馈和数据

**一句话**：学习者在 App 里举报有问题的卡，编辑在控制台处理；控制台还能看学习数据、管理对外 webhook、查看自动化做了什么。

**先懂几个词**
| 词 | 大白话 | 类比 |
|---|---|---|
| advisory lock（建议锁） | 数据库提供的一把"自己起名字"的锁。代码先拿锁，再查重、数数、写入。别的请求想拿同一把锁，就得排队等。 | 洗手间只有一把钥匙，拿到钥匙的人才能进去 |
| 部分唯一索引（partial unique index） | 只对满足条件的行要求"不能重复"。比如只管还没处理（open）的举报，处理完的旧举报不算。 | "每人同时只能挂一个号"，看完病的旧号不算 |
| 事务性 outbox（待发箱） | 要通知外部的消息，先和业务数据在同一个事务里写进一张"待发"表，提交后再真正发出去。 | 寄信前先在登记簿上记一笔，邮差没来，记录也丢不了 |
| dry_run（演习模式） | 系统照常做判断，但只记下"本来会怎么做"，不真的执行。 | 消防演习：流程全走，但没有真着火 |

**一步一步发生了什么**
1. 学习者在 App 里举报一张卡。登录用户选原因，还能写备注；没登录的人只能选结构化的原因，不能写备注。两个入口写进同一张 `card_reports` 表。
2. 后端开一个事务，先拿 advisory lock。登录用户每人一把锁；匿名举报全站共用一把。拿到锁后，查重、数今天的条数、插入，三步看到的是同一批数据。例子：小王 1 秒内对第 9 张卡点了两次举报。第二个请求要等第一个提交，然后发现已有一条未处理的举报，就直接返回那一条，不新建。
3. 防刷上限：登录用户每天最多 5 条，匿名举报全站每天最多 100 条，超了返回 429。数据库再兜底：同一用户同一张卡只能有 1 条未处理；匿名对同一张卡、同一原因每天只能 1 条。这两条都是部分唯一索引。
4. 编辑在 `/reports` 按状态和卡组筛选，跳到卡片编辑器改卡，再选 fixed / wont_fix / duplicate / invalid 关闭。页面从不显示举报人是谁。关闭是一条带条件的 UPDATE：只改还没处理的那条。两个人同时关同一条，后到的收到 409。
5. 学习数据：App 把复习事件同步上来。automation tick（每 15 分钟跑一次的后台任务）里有一步 analytics_daily：每个 UTC 日只在第一次到期时运行，把复习事件汇总进 `analytics_daily`，每次重算最近 8 个完整的 UTC 日。页面 `/usage` 显示 DAU / WAU / MAU（截至当天的 1 天、7 天、30 天内有复习的不同用户数），以及 D1 / D7 留存（某天第一次复习的新用户里，恰好在第 1 天、第 7 天那一天又复习了的比例；那一天没过完之前显示为空）。按卡组的数字在请求时实时算，不是 super_admin 的人只看到自己能读的卡组。匿名漏斗表不存任何用户或设备 ID，保留 400 天。
6. 对外通知和自动化：`deck.published` 和发布在同一个事务里写进待发箱，提交后再发到消息队列 SQS；VPC 外的 Python 投递程序用密钥签名后发出去。webhook 地址必须是 https，并且拦截内网和本机地址。自动化在生产是 dry_run：照常做判断，把"本来会怎么做"（比如 would_publish）记进自动化自己的决策记录，但不真的自动接受或发布，账本里也不会因此多出自动接受、自动发布的记录。

**为什么这样设计**
- 问题是"先查再插"有竞态：两个请求同时查，都发现没有，就都插进去了。所以用 advisory lock 让同一个人的请求排队，部分唯一索引做最后一道墙。取舍：匿名举报全站共用一把锁，所有匿名请求（包括最后被判为重复或超上限的）都要排队一个一个过；但网关对这条路由限流为每秒 2 个、突发 5 个，每个容器每分钟最多 30 个，每天最多新建 100 条，排队的量很小，可以接受。
- 问题是发布成功要通知外部，但通知不能拖垮发布，也不能发布回滚了却把通知发出去。所以 `deck.published` 用事务性 outbox。取舍：其他事件只是尽力而为，业务提交后先写投递记录再发 SQS；发送失败的行要手动重扫补发。
- 问题是 AI 自动接受、自动发布有风险。所以生产先跑 dry_run，草稿仍由人审核，系统只记"本来会怎么做"。取舍：dry_run 期间自动化不替人做任何事，人工量一点没少；要切 live，还得先通过评测门槛（最新一次评测通过且没被撤销）。另外，账本里的"省下的时间"只是估算（件数 × 基线分钟数 − 实际分钟数，不低于 0），而且是查询时按当前基线现算的。

**面试官可能追问**
1. 已经有 advisory lock 了，为什么还要部分唯一索引？
   锁只保护走这段代码的请求，索引是数据库自己的规则，任何写入都绕不过去。匿名入口如果真撞上索引，代码把它当成重复，照样回"已收到"。
2. 为什么每次要重算最近 8 天，而不是只算昨天？
   App 可能晚几天才把复习同步上来，而 D7 留存要等 7 天后才知道。重算是覆盖写（有就覆盖、没有就插入），跑几次结果都一样。

**English**
"After publishing, learners can report a card from the app, signed in or anonymously; daily caps are counted in code under an advisory lock, and partial unique indexes allow one open report per learner and card. Editors resolve reports in the console, and webhooks go out through SQS and a signing dispatcher."

### 10. 管理和审计

**一句话**：账号权限和数据库迁移只有 super_admin 能做；14 种关键管理操作会和业务在同一个事务里写进一张只能追加的审计表。

**先懂几个词**
| 词 | 大白话 | 类比 |
|---|---|---|
| 事务（transaction） | 一组数据库修改，要么全部成功，要么全部撤销，不会只做一半。 | 银行转账：扣钱和加钱必须一起发生 |
| pg_advisory_lock（迁移锁） | 一把用固定编号的数据库锁。它本身不锁任何表，只拦住另一个也想跑迁移的请求。 | 机房门口一块"正在施工"的牌子，同一时间只能挂一块 |
| 常量时间比较 | 比较两个字符串时，不管第几个字符不同，花的时间都一样。攻击者就没法靠测响应快慢，一位一位猜出密钥。 | 开锁时不管哪一齿不对，都等同样久才告诉你"错" |
| 触发器（trigger） | 挂在表上的自动规则。有人想改、删或清空这张表，它先跑，直接报错。 | 账本每页都盖了"只许往后写、不许涂改"的章 |

**一步一步发生了什么**
1. 权限：super_admin 在 `/admin/users` 页，按 Cognito sub（登录系统给每个账号的唯一 ID）给账号分配卡组的读写权限。后端先确认调用者是 super_admin，再在一个事务里改 `admin_deck_permissions`，同时写一条审计，记下改前和改后。账号本身的创建和删除不在控制台做：owner 在开了 MFA（多一步验证）的会话里用 AWS CLI 操作。原来负责建号的 Lambda 已在 10-04 下线。
2. 迁移（改数据库结构的 SQL 文件）不在部署时自动跑，要 super_admin 在控制台点按钮触发。后端依次检查三件事：调用者是 super_admin；迁移密钥正确（常量时间比较）；拿到 pg_advisory_lock。
3. 然后逐个执行还没跑过的文件。一共 46 个，原则上只做加法。每个文件、它在 `schema_migrations` 里的版本记录、它的审计行，在同一个事务里提交。例子：跑到第 44 个文件出错，这个文件整体回滚，版本号也没记上；前面已提交的不受影响，下次点按钮会从第 44 个重来。（第 45 个是唯一标了 destructive 的文件，按钮会停在它前面，不会执行它。）
4. 遇到标了 destructive（会删数据、改坏旧结构）的文件，就停在它前面，后面的也不跑。必须显式确认它的版本号才执行。控制台按钮不带这个确认，所以按钮跑不了破坏性迁移。
5. 审计：每次关键操作在 `admin_audit` 写一行：谁、做了什么、对什么、改前改后，以及 traceId（这次请求的追踪号，能和日志对上）。它和业务修改在同一个事务里：业务回滚，审计一起回滚；业务提交了，审计一定在。触发器禁止 UPDATE、DELETE 和 TRUNCATE，所以这张表只能追加。

**为什么这样设计**
- 问题是审计如果单独写，可能出现"业务成功但审计丢了"，或"审计写了但业务回滚了"。所以放进同一个事务。取舍：只覆盖 14 种操作。删除卡组、删除卡片、发布、处理举报都不写这张表；发布记在 `deck_publishes`，草稿审核记在 `ai_review_events`。
- 问题是迁移会动整个数据库，两个人同时跑、或部署时悄悄自动跑，都很危险。所以手动触发：先过两道检查（super_admin、迁移密钥），再拿一把迁移锁，破坏性迁移还要点名确认版本号。取舍：每次部署后要有人记得去点按钮。
- 问题是建号删号的权限太大。所以把它移出控制台，由 owner 在 MFA 会话下用 AWS CLI 做。取舍：多一步手工操作，但控制台里少了一个可被滥用的入口。

**面试官可能追问**
1. 审计日志怎么保证不被改？
   它和业务写在同一个事务里，数据库触发器禁止改、删和清空。要坦白：删除卡组这类操作没写进这张表，控制台也还没有查看审计日志的页面。
2. 两个 super_admin 同时点迁移会怎样？
   第二个请求卡在拿锁这一步，不会两个同时执行。它最多等 20 秒（连接的 statement_timeout），等不到就报错返回，什么也不做；等到了，会先重新查哪些版本已经跑过，所以不会重复执行同一个文件。

**English**
"Only super admins manage deck permissions and run migrations, which take an advisory lock and stop before anything destructive unless you confirm its exact version. Fourteen kinds of admin action, such as permission changes, rollbacks, migrations and webhook changes, are written in the same transaction to an append-only audit table protected by triggers."

### 11. 横切：前端工程

**一句话**：控制台加载快，编辑不会丢，失败的写请求不会被自动重放，安全策略在测试里真正跑过。

**先懂几个词**
| 词 | 大白话 | 类比 |
|---|---|---|
| 代码拆分 / 懒加载 | 不把所有页面一次下载完。用户进到哪个页面，才下载那个页面的代码。 | 自助餐不一次端上所有菜，点哪道才上哪道 |
| 首屏预算 | 给"第一次打开要下载多少字节"定一个上限，写成测试，超了就不让合并。 | 行李限重 23 公斤，超了不让登机 |
| 幂等 / 重放 | 幂等：同一个请求做一次和做两次，结果一样。重放：把同一个请求再发一遍。不幂等的写请求被重放，就可能写两遍。 | 付款按钮点两下，可能扣两次钱 |
| CSP（内容安全策略） | 服务器随网页一起下发的白名单：页面只能从哪里加载脚本、只能连哪些地址。名单外的，浏览器直接拦。主要防 XSS，也就是别人往页面里塞恶意脚本。 | 门卫手里的访客名单 |

**一步一步发生了什么**
1. 编辑第一次打开控制台（React 19 + TypeScript 的单页应用，用 Vite 打包）。浏览器只下载入口代码。登录页和登录回调页直接打在入口里，因为没登录的人只会落到这两页。其余 16 个页面按需下载。首页卡组列表的代码在启动时就提前开始下载，登录完基本已经到了。
2. 这个"快"有测试守着。CI 真实跑一次生产构建，把入口脚本、index.html 列出的样式和预加载文件，以及它们静态引用到的全部 JS 加起来，超过 377,000 B 就失败；今天是 370,892 B。按需加载的页面和预取的卡组列表都不算在内。登录页真正下载的量（加上预取的卡组列表那条链）另有一个 487,000 B 的预算，今天约 484,690 B。它还检查 highlight.js 没有回到首屏，也没有混进登录页的预取链。axios 只检查它还在构建产物里，并不检查它在不在首屏；实际上登录页预取卡组列表时，会把 axios 一起下载下来。
3. 编辑打开卡片列表。React Query 把读到的数据存在浏览器里，30 秒内再回来就不重新请求。没有 Redux 这类全局 store。保存一张卡后，只让受影响的那几份缓存失效。
4. 编辑改到一半想离开。"未保存修改"守卫会拦下。站内跳转由路由库的拦截功能挡住（useBlocker；它只能在 react-router 的"数据路由"模式下用，所以入口换成了这种路由）。关标签页或刷新时，浏览器弹出"确定离开吗"（beforeunload）。
5. 保存时网络超时。React Query 不会自动再发一次，因为请求可能已经落库。单卡保存有版本号保护（新建有 (deck_id, stable_uid) 唯一约束），重放不会写两遍，但会对一次其实已经成功的保存报 409 冲突。没有这类保护的写请求，重放才可能真的重复写。所以写请求一律不自动重试，让用户看到结果后自己决定。读失败也不自动重试，因为服务器拒绝了就是答案。用户看到错误，自己决定要不要再点。
6. 发新版控制台时：文件名里带内容哈希的 JS、CSS（内容一变，名字就变）缓存一年；`index.html` 不缓存、最后上传。旧的哈希文件故意保留，已经打开的老页面通常还能加载。上传后刷新 CloudFront，再读回线上的 `index.html` 核对哈希。万一某个页面的代码块还是下载失败，页面提示用户刷新，而不是白屏。

**为什么这样设计**
- 问题是：拆分以前，所有页面挤在一个 553,688 B 的包里，登录页也要等它下载完。所以按页面拆分，再把预算写成测试，防止以后悄悄变胖。代价是多了一种失败：页面代码块可能下载不到。所以加了"提示刷新"的兜底；而且必须整页刷新，只重新渲染没用，因为 React 会记住上次加载失败的结果。
- 问题是：写请求超时，不代表服务器没写进去。所以写请求一律不自动重试。代价是网络抖一下，用户要自己再点一次。批量导入是例外：它按 stable_uid 幂等，重试安全，所以导入器自己按 1 / 2 / 4 秒退避重试。
- 问题是：登录 token 放在 sessionStorage，页面里的 JS 读得到，一旦被注入脚本就可能被偷。所以由 CloudFront 下发严格的 CSP 来降低这个风险：`script-src 'self'`，不许内联脚本，connect-src 只允许连控制台自己的域名（'self'）、自己的 API、Cognito 和 Sentry（错误上报服务）。Playwright 在同一套响应头下跑测试，出现任何 CSP 违规就失败。代价是以后每加一个第三方脚本或地址，都要先改白名单。

**面试官可能追问**
1. **你说写请求不重试，那批量导入为什么会重试？** 因为导入是幂等的：按 stable_uid 对账，已经落库的批次重发一次，结果全是"不变"。普通的单卡保存不是这样：重放虽然不会写两遍，但会对一次其实已经成功的保存报 409 冲突，所以不自动重试。
2. **首屏 377 kB 是怎么量的？为什么不直接看 Vite 打印的大小？** 测试从构建出的 `index.html` 出发，把入口脚本、样式和它们静态引用到的全部文件加起来，按需加载的页面不算。Vite 会把每个文件的大小逐行列出来，但不会把首屏要一起下载的文件加起来。只看入口块那一行很容易被骗：试过一种简单的 manualChunks 写法，入口块只显示约 17 kB，浏览器实际仍要下载约 402 kB，因为拆出去的 vendor 块是入口的静态依赖。

**English**
"The console is a React 19 SPA with sixteen lazy-loaded pages. CI fails if the first-load bundle goes over a byte budget, and Playwright runs against the production security headers, so any CSP violation fails the build."

### 12. 横切：后端与数据库

**一句话**：一个 .NET Lambda 处理全部控制台 API，数据放在不对公网开放的 PostgreSQL；慢查询和挂起的事务都有服务端超时。

**先懂几个词**
| 词 | 大白话 | 类比 |
|---|---|---|
| Lambda 容器 | AWS 按需启动的一小份运行环境。一个容器同一时间只处理一个请求，闲久了会被回收。 | 临时工：来活才上岗，一次只干一件事 |
| 挂起的事务 / 服务端超时 | 事务是一组要么全做、要么全不做的数据库操作。挂起的事务：开了头，却一直不提交也不回滚，还占着锁。服务端超时是数据库自己的闹钟，到点就取消语句或断开连接，不靠客户端。 | 有人把购物车停在收银台就走了，后面全堵着；店员到点把车推走 |
| 部分唯一索引 | 只对满足条件的那几行要求"不能重复"。比如"进行中"的发布每个卡组最多一条，已完成的历史随便多少条。 | 每家只能占一个临时车位，长期车位不限 |
| SQS / NAT | SQS 是 AWS 的消息队列：先把活儿记下来，后台慢慢做。VPC 是 AWS 里的私有网络；NAT 是它通向公网的出口，没有它，VPC 里的程序上不了外网。 | 餐厅的点菜单 / 大楼唯一的对外大门 |

**一步一步发生了什么**（例子：编辑保存第 9 张卡）
1. 请求过了 API Gateway，进到 core-vpc：一个 .NET 10 的 arm64 Lambda，512 MB 内存（原来是 128 MB，一次冷启动约 1 秒初始化，再加第一个请求约 3.7 秒，所以调大了；调大后没有重新测）。它先看请求体，超过 1 MiB 直接返回 413。再按路径后缀逐条匹配手写的路由，没有用 ASP.NET 框架。
2. 处理函数用这个容器唯一的一条连接，去连 RDS 上的 PostgreSQL 17。数据库不对公网开放、存储加密、自动备份保留 14 天。1 条连接就够，因为一个容器同时只处理一个请求。core-vpc 最多 40 个容器同时运行，所以 API 最多 40 条连接，在应用数据库账号 50 条的上限以内。
3. 这条连接一建立就带着两个服务端超时。一条 SQL 跑超过 20 秒，数据库自己取消它。一个事务开着却闲置超过 60 秒，数据库断开连接、回滚、放掉锁。例子：导入一批卡时，整批在一个事务里写，还锁着卡组那一行。如果 Lambda 在事务中途超时或崩了，就没人发提交。没有这个设置，这个事务能挂到 RDS 默认的 24 小时，一直锁着这批卡和卡组；现在 60 秒后就会被清掉。单卡保存是一条自动提交的 UPDATE，不会留下挂起的事务，它只受 20 秒语句超时约束。
4. 写入时，关键规则由数据库约束兜底。表按业务分几组（表速查）：
   - 内容：`decks`（slug 唯一；`live_build_id` 指向线上构建；`is_deleted` 只打删除标记、不真删）；`cards`（(deck_id, stable_uid) 唯一、(deck_id, order_in_deck) 唯一；`version` 版本号防止后保存的人悄悄覆盖）。
   - 权限：`admin_deck_permissions`，(admin_sub, deck_id) 唯一。
   - 发布：`deck_publishes`（任务 + 构建历史；部分唯一索引让每个卡组最多一个 PENDING / PROCESSING）；`deck_build_patches`（两个构建之间的增量补丁，(slug, from, to) 唯一）。
   - AI：`ai_drafts` / `ai_review_events`（(deck_id, client_draft_key) 唯一；审核事件只能追加）；`ai_qa_runs` / `_items` / `_findings`（每个卡组最多一个进行中的质检）；`card_embeddings`（每张卡一串 384 个数字的向量，用来找意思重复的卡）。
   - 发布后：`card_reports`（每人每卡最多一条未处理举报；匿名举报每卡每原因每天最多一条）；`analytics_daily` / `anon_funnel_events`（漏斗表不含任何身份 ID）；`webhook_subscriptions` / `webhook_deliveries`（对外 webhook 的待投递表，订阅只打删除标记）；`automation_events` / `automation_baselines`（自动化账本，`dedupe_key` 唯一）。
   - 管理：`admin_audit`（数据库层禁止修改和删除）；`schema_migrations`（版本号是主键）。
5. 结果包成统一的信封 `{success, data, error, traceId, version}` 返回。前端读其中四个字段，变成 `ApiResult`；出错时也返回这个对象，不向页面抛异常。页面按错误码分情况处理，traceId 把用户看到的错误和服务器日志对上。
6. 慢的活不在请求里做，因为网关 30 秒就超时：发布、AI 质检、webhook、邮件都先发到 SQS，由后台 Lambda 处理。VPC 没有 NAT，需要上外网的工作（比如调模型、投递 webhook）交给 VPC 外的 Python Lambda，结果通过带签名的内部接口报回 core。

**为什么这样设计**
- 问题是：这是只给内部编辑用的后台，流量很小。所以全部控制台 API 放在一个 Lambda 里，配一个私有数据库，部署和排查都只看一处。代价是所有路由共用一份并发额度（最多 40 个容器）；数据库是单 AZ（只在一个机房）、最小规格的 db.t4g.micro，不能当容量或高可用证明。
- 问题是：客户端超时只在 Lambda 活着时有用。Lambda 超时、崩溃或被冻结后，它留下的语句和事务没人收尾，一直占着锁和连接。所以把超时设在数据库服务端，写进连接的启动参数，连接被复用也还在。20 秒低于网关的 30 秒（过了 30 秒，调用方已经拿不到答案），也是实测最慢路由 9.1 秒的两倍多；60 秒是网关超时的两倍。worker 两项都是 600 秒，因为发布构建允许跑更久（实测最慢只有 4.6 秒）。代价是：真需要更久的操作要在事务里自己放宽，比如数据库迁移。
- 问题是：代码里"先查再写"在并发时会漏，两个请求可能同时查到"没有"。所以关键规则直接写成数据库约束：唯一键、部分唯一索引、审计表禁止改删。代价是改规则要写迁移。

**面试官可能追问**
1. **为什么每个容器只开 1 条连接？** 一个 Lambda 容器同一时间只处理一个请求，多开的连接用不上，只会占数据库名额。core-vpc 最多 40 个容器，所以最多 40 条连接，低于应用账号 50 条的上限。
2. **数据库只有单 AZ，挂了怎么办？** 我会直说：现在流量很小，只开了单 AZ，靠加密存储、14 天自动备份、删除保护和一次实测的恢复演练（约 27 分钟恢复，最多丢约 8 分钟数据）兜底，这不能当高可用证明。真要扩，第一步是开 Multi-AZ。

**English**
"The backend is one .NET 10 Lambda with a hand-written router in front of a private PostgreSQL instance. Every API connection gets a 20-second statement timeout and a 60-second idle-in-transaction timeout, the publish worker gets 600 seconds, and anything slow runs through SQS."
