# B11 — Cleanup: delete the Lottie era, trim the ceremony styles, cap the shadows (`cleanup-lottie`)

Delete `CeremonyLottie.tsx`, the `HolographicLayer.tsx` shim, `assets/lottie/*` and `scripts/gen_lottie.py` once B09 has stopped importing them (and drop the one `foilLayer.test.tsx` case that imports the shim) · trim `ceremonyStyles.ts` to the keys the new ceremony actually references and `FeaturedCard.tsx` to what it renders · remove every `shadowRadius ≥ 16` in the gacha/ceremony tree (design perf budget) so `grep -rnE "shadowRadius: *(1[6-9]|[2-9][0-9])"` over that tree is empty and every `shadowRadius` that survives inside the ceremony tree is ≤ 8.

## Context

The shipped 1.5.0 ceremony is carried by a LottieFiles gift-box animation and a hand-rolled `Animated` fallback that live in one 1132-line file, `mobile/src/components/CeremonyLottie.tsx` (design §1, `docs/release-1.6.0-plan-2026-09-19.md:10`, `:24`; audit table `:39-41`). Seam of Light replaces all of it (design §3, `:85`: "**删除**：`lottie-react-native`、`assets/lottie/*`、`gen_lottie.py`、SparkleField / ParticleBurst / MultiPackFlyIn、33 ms 的 orbit setInterval、滑块控件、15 处 shadowRadius"). By the time this issue runs, B01 has removed the `lottie-react-native` package (`mobile/package.json:41` today; B00 §0), B08 has reduced `HolographicLayer.tsx` to a one-line re-export shim over `FoilLayer` (B00 §2.11), B08 has created `ceremony/ceremonyStyles.ts` from the `tapCard*` subset of `CeremonyLottie.tsx:1001-1117`, and B09 has rewritten `DrawCeremonyScreen.tsx` so that it imports nothing from `CeremonyLottie` or `HolographicLayer` (B00 §3.2 grep contract) and has created `ceremony/FeaturedCard.tsx` from the static `RevealCard` (`CeremonyLottie.tsx:271-409`; B00 §2.12). What remains is dead weight: a component whose guarded `require('lottie-react-native')` (`CeremonyLottie.tsx:37`) can never succeed, a **static** `require('../../assets/lottie/pack-opening.json')` (`:44`) that keeps 84 KB of JSON in the bundle, a shim nobody imports, a generator script with a hard-coded container path (`mobile/scripts/gen_lottie.py:16`), and — because every style key was copied first and pruned never — a `ceremonyStyles` table full of `halo*`/`sparkle*`/`orbit*`/`flyIn*`/`flip*` keys and seven `shadowRadius ≥ 16` styles (`CeremonyLottie.tsx:660, :716, :744, :790, :799, :850, :971` — the last is `flashCore`'s `shadowRadius: 40`, `:961-972`).

The shadow rule is a performance rule, not a taste rule. Design §3.5 (`:133`) bans "RN shadowRadius ≥ 16 (flashCore shadowRadius 40 CeremonyLottie.tsx:969-971 and the 15 shadowRadius sites removed; ≤ 3 shadowed RN views with shadowRadius ≤ 8)": a large `shadowRadius` on iOS is a per-frame Gaussian blur of the view's alpha mask on the render server, and during tear/spill several such views animate at once. The tree has 23 sites ≥ 16 under `mobile/src`; 12 of them are in the gacha/ceremony tree (B00 §7.4, §9 #8): the seven above die with `CeremonyLottie.tsx`, and the other five are `DrawScreen.tsx` `stateCard` (`:893`, 18) and `packShadow` (`:993`, 22), `drawResultStyles.ts` `featured` (`:138`, 22) and `modalCard` (`:559`, 24), `RewardSummaryCard.tsx` `card` (`:108`, 16). Screens outside that tree (`AuthGateModal`, `WelcomeScreen`, `HomeScreen:1041`, …) stay as they are — Wave B does not touch them.

This issue depends on B09 (and, through it, on B08's `ceremonyStyles.ts`/shim and everything below). It creates nothing; it deletes, trims and caps. Every deletion is safe only because nothing imports the deleted module any more — the verify proves that with greps before it runs a single test. One test does import the shim: B08's `mobile/tests/unit/foilLayer.test.tsx` carries a third case, `'HolographicLayer shim forwards to FoilLayer'`, whose only purpose was to prove the shim kept the pre-B09 screen compiling (B08 brief, Changes 6.3). Nothing else references the shim after B09, so that case — and only that case — is deleted here together with its `import { HolographicLayer, skiaAvailable } from '../../src/components/HolographicLayer'` line (B00 §1 row `mobile/tests/unit/{tapCard,foilLayer}.test.tsx`, §2.11, §7.2). Cases 1 and 2 (`'renders null under vitest and never touches the Skia clock'`, `'prewarmFoilShader is a no-op without Skia and never throws'`) stay byte-identical.

The design's "≤ 3 shadowed RN views" (`:133`) is a count of *rendered* views on device, not of style keys in a file: after B08 + B09, `ceremonyStyles.ts` legitimately carries several small shadows (`tapCardFace` 6, `tapCardShadow` 6, `stageCard` 8, `swipePackInner` 8, `skipButton` 6, `ceremonySkipX` 6, …) of which only a few are mounted in any one phase. That device count is reviewed under B14's rubric (`A-P0-CANVAS-BUDGET`); what this issue enforces mechanically is the static gate the design's DoD states (`:187`, "no shadowRadius ≥ 16 in the ceremony tree") tightened to "every surviving `shadowRadius` in the ceremony tree ≤ 8".
