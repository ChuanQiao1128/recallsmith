> 这份文档是 `01-csharp-backend.md` / `02-react.md` / `03-cloud-aws-azure.md` / `04-databases.md`
> 四份材料的**使用说明**。四份材料本身是内容,这一份是方法、顺序和验收标准。
>
> **读者定位(先把这句放在最前面):**
> 你不是初学者。三个 AWS Lambda + PostgreSQL + SQS worker + S3 的内容系统、
> 一个跑在 Azure 上的付费 SaaS、三个 React/React Native 应用加一个管理控制台,
> 这些都是你自己从零造出来并跑在生产上的。
> 所以这四份材料**不教你怎么做**,它教你**这些东西叫什么名字、为什么这样设计、
> 什么时候会坏、别人常常在哪里误解**。

> 你的洞不在"没摸过",在"讲不清"。转行者在面试里被重点验证的恰好就是这一点:
> **面试官不是在查你会不会,是在查你是真懂还是背的。**
> 而"真懂还是背的"这个判据,只有一个可靠的外部表现:**你能不能不看稿子讲清楚。**

## 一、学习方法:为什么要手动录卡

### 手动录入是刻意设计,不是工具没做好

这四份文档给出的是**卡片素材**,不是成品卡组,也不提供导入文件。这是故意的。

**Mental model:阅读是把知识放进房间,改写是把知识搬进身体。**

心理学上这叫**生成效应(generation effect)**:自己生成出来的内容,
记忆强度显著高于同等时间阅读到的内容。
录卡这个动作里真正起作用的不是"打字",是**你被迫把一段答案压缩成自己的句子**。
压缩过程中会发生三件事:

1. **暴露伪懂。** 你读的时候觉得"这个我懂",一旦要改写就卡住,说明你懂的是句子不是概念。
   卡住的那一刻是这套方法最值钱的时刻,不要跳过去,回到 `### 概念讲解` 重读那一段。
2. **建立你自己的措辞。** 面试时你不会说出文档里的句子,你会说出你自己练过的句子。
   录卡就是在提前生产面试时的口头语料。
3. **筛掉不该留的卡。** 你如果改写不出来又觉得它不重要,就删掉。
   你是这副卡组的第一个用户,也是唯一的编辑。

所以:**录入时请用自己的话重写 A 面。照抄等于把知识搬进了软件,没搬进你脑子。**
EN 那一行同理,不要照抄,改成你自己的语气,能脱口而出的才算数。

### 每日循环(约 50 分钟)

| 步骤 | 时长 | 做什么 | 判断"这一步做到位了"的标准 |
|---|---|---|---|
| 1. 读概念 | 20 min | 读当天模块的 `### 概念讲解`。遇到锚定你自己代码的地方,**把那个文件真的打开放旁边对着看**。 | 你能对着自己的代码指出"这段就是文档里说的那个机制"。 |
| 2. 录卡 | 20 min | 录当天模块的 6-10 张卡,**A 面用自己的话重写**。 | 你至少有 2-3 张卡的 A 面和原文长得不一样。全都一样 = 这一步白做了。 |
| 3. 复习 | 10 min | 在 App 里过完当天到期的卡。**先盖住答案自己讲一遍,再翻。** | 你在翻答案前先出声或在心里完整答了一遍,而不是"看一眼就点会了"。 |
| 4. 出声解释 | 5 min | 挑当天**最难的一张卡**:EN 句朗读三遍,然后对着手机录音,**用中文或英文展开解释 60 秒**,回听一遍。 | 回听时你能听出自己哪里卡壳、哪里在绕、哪里说了废话。 |

### 第 4 步是转行者的胜负手

这一步看起来最像可以省的那一步,实际上它是全部四步里唯一直接对应面试场景的那一步。

理由很直接:**面试不考你认不认识一个概念,考你能不能解释它。**
认识和解释之间隔着一层,这一层叫"提取并组织成口语的能力",
它只能靠"出声练"来长,靠"读"和"点会了"长不出来。

而且转行者在这一点上被更严格地检验。
CS 科班背景的候选人说一句半通不通的话,面试官倾向于认为他表达没组织好;
转专业候选人说同样一句话,面试官倾向于认为他不懂。
**这不公平,但它是真实的评分环境,唯一的应对是把解释练到明显流畅。**

回听是必须的。你会发现三种典型问题,它们在你脑子里都察觉不到:

- **绕圈**:解释 A 的时候用了 B,解释 B 的时候用了 A,一句实质信息都没给。
- **跳层**:直接跳到实现细节,没先给一句让人能挂住的 mental model。
- **停顿在同一个位置**:每次都卡在某个具体概念上,那就是你真正的洞,单独拎出来补。

录音不需要留着,听完就删。**它的价值全在"听到自己"这一下。**

## 二、学习路线:六周节奏

### 排序原则

模块顺序不按支柱走,按**"NZ intermediate 面试频率 × 你的现有实感"**穿插排:

1. **C#-1/2 与 React-1/2 先行。** 类型系统/内存、async/await、渲染模型、state 与 props
   是四份材料里被后面所有模块反复引用的地基。它们也是面试里出现频率最高的一组,
   几乎每一轮技术面都会碰到其中至少两个。
2. **数据库-2/3 紧跟。** 索引和事务隔离是 intermediate 岗位的分水岭题:
   junior 答不出,senior 答得太抽象,intermediate 恰好被要求"讲得具体"。
3. **云-4(队列与消息)放中段提气。** 这是四份材料里离你自己代码最近的一块
   (SQS worker、outbox、event_id 幂等),读起来会有"这个我早就做了,只是不知道它叫这个"的爽感。
   把它放在第三周,正好接住前两周啃地基的疲劳。
4. **C#-7(ASP.NET Core)和云-1/6(权限、网络)放中后段。**
   这三块是你经验相对薄、而面试官最爱用来分辨"真部署过还是只写过代码"的地方,
   需要前面的模块先把周边知识铺好,不然会读成孤立的名词表。
5. **成本、可观测、NoSQL 放最后。** 它们依赖前面全部具体系统才有意义,
   而且是面试里的加分项而非淘汰项,晚一点学不影响。

### 六周表

每周 5-6 天,每天一个模块。每周留 1-2 天做纯复习(不录新卡)和第四节的白板自测。

| **第 3 周:你的主场** | **C#-6 数据访问 Npgsql/ADO.NET (10)**<br>**DB-4 并发控制 (11)**<br>DB-5 查询能力 CTE/EXPLAIN (12)<br>**云-4 队列与消息 (10)**<br>React-5 性能 (9) | **52** |

**加粗的模块是"简历引力"模块**,理由见第五节。它们值得多花一天,
或者在录完之后额外做一次白板自测。

节奏说明:

- 每周约 50 张新卡,加上复习队列,单日总量稳定在 50 分钟左右。
- 第 5、6 周每周 6 个模块,单卡量略高,但那时你的复习队列里早期卡片已经拉长间隔,
  实际总时间不会明显增加。
- **如果某周落后了,砍掉的应该是新卡而不是复习。**
  少录五张卡损失很小,断三天复习会让前面两周的卡集体到期堆积,那是最容易放弃的场景。

## 四、解释练习协议

### 规则

每个模块录完卡的第二天(不是当天,要隔一次睡眠),做一次白板自测:

1. 从下面的清单里挑该模块的题,**每题对着白板/纸/空墙讲 2 分钟**,不看文档,不看卡。
2. 讲完之后再翻文档核对。
3. **三层判据,三层都说到才算过:**

| 层 | 你必须说出的东西 | 没说到的典型表现 |
|---|---|---|
| **1. Mental model** | 一句有画面感的概括,让不懂的人也能挂住。 | 一上来就说 API 名字和参数。 |
| **2. 为什么** | 这个设计在解决什么问题,替代方案是什么,取舍在哪。 | 只说"它就是这么设计的"或"最佳实践是这样"。 |
| **3. 什么时候坏** | 一个具体的失败场景:什么条件下这个机制不成立或产生 bug。 | 只会说"用得不对就会有问题",给不出条件。 |

**没过就是没过,不要给自己打折。** 判据里最常被跳过的是第 3 层,
而第 3 层恰恰是面试官区分"真懂/背的"的主要手段:
背下来的人能说对定义,只有真用过并想清楚的人说得出边界。

## 五、与面试的连接:简历引力

### 什么是"简历引力"

面试官准备技术问题的成本很高,所以绝大多数人会走一条省力路径:
**从你简历上写的名词开始往下挖。**
你简历上写了什么,面试的技术深度问题就大概率长在那上面。这叫简历引力。

你的简历上有这几个高引力名词:

- **idempotent(幂等)** / `event_id` 去重
- **transactional outbox**
- **per-column LWW(last-write-wins)合并**
- **keyset 分页**
- **原子摄入 / 单条 SQL 多 CTE**
- **Stripe 幂等计费、HMAC webhook**
- **health-gated CI/CD**

这些词的共同点是:**它们都是"听起来懂的人才会写"的词。**
面试官看到它们的反应不是"哦这人会",而是"我倒要问问他是不是真的懂"。
所以它们既是你最大的加分项,**也是你最大的风险点**:
写了却答不深,比没写更糟,因为那会被读成"简历是包装出来的"。

### 最高优先模块(简历引力模块)

这些模块请**多花一天**,并在录完卡后额外做一次白板自测:

| 优先级 | 模块 | 对应你简历上的哪句话 | 面试官最可能追问的方向 |
|---|---|---|---|
| **P0** | **DB-4 并发控制** | per-column LWW 合并、outbox 认领 | "两个设备同时提交同一张卡的进度,谁赢?为什么不用版本号?"<br>"你的 outbox 发布器崩了那行怎么办?" |
| **P0** | **DB-3 事务与隔离级别** | 6-CTE 原子摄入 | "你用的什么隔离级别?为什么 Read Committed 就够?"<br>"如果两个请求同时到,会不会算错?" |
| **P0** | **云-4 队列与消息** | SQS worker、transactional outbox、event_id 幂等 | "为什么需要 outbox,直接在事务里发消息不行吗?"<br>"至少一次投递下你怎么保证不重复处理?" |
| **P0** | **C#-6 数据访问** | 6-CTE 单条 SQL、Npgsql | "为什么写成一条 SQL 而不是四条语句包一个事务?"<br>"Lambda 里连接池怎么配的?" |
| **P1** | **DB-8 选型与一致性** | per-column LWW 的算子选择 | "为什么有的列用 greatest,有的列用相加,有的列用集合并?" |
| **P1** | **DB-2 索引** | keyset 分页 | "为什么不用 OFFSET?你的游标里有哪几个字段,为什么?" |
| **P1** | **云-2 计算光谱** | 三个 Lambda 的分层(Public / Vpc / Worker) | "为什么拆成三个函数?冷启动怎么处理?" |
| **P1** | **React-7 TypeScript in React** | 判别联合建模(`DeckAction`) | "你怎么用类型防止非法状态?为什么有的模型没这么做?" |

### 怎么用这张表

1. **P0 的四个模块,在开始投递之前必须过完并通过白板自测。**
   它们对应的是你简历上最显眼的四个技术声明,任何一轮技术面都可能问到。
2. 每个 P0 模块,准备一段 **90 秒的第一人称叙述**:
   我遇到了什么问题 → 我考虑过哪几个方案 → 我为什么选了这个 → 它在什么条件下会不成立。
   这四段正好覆盖白板自测的三层判据,加上一层"我做的"。
3. **主动埋钩子。** 讲完一个答案后可以留一句
   "这里其实还有个边界情况,是关于 X 的",让面试官顺着问下去。
   引导追问方向到你准备过的地方,是转行者能用的最有效的场上策略。
4. 反过来:**如果某个模块你怎么都练不到能讲 2 分钟,考虑把对应措辞从简历上弱化。**
   简历应该只写你能被追问三层的东西。这不是心虚,这是控制暴露面。

## 六、开始前的三个提醒

1. **不要通读四份文档再开始录卡。** 通读会给你"我都懂"的错觉,
   而这个错觉正是转行者在面试里被打穿的原因。一天一个模块,读完立刻录,录完立刻讲。
2. **卡片是活的。** 复习时觉得某张卡"问得不对"或"太简单了",第二天就改或删。
   一副没被修改过的卡组,说明你没在用它思考。
3. **录音那五分钟不要省。** 它是唯一一个把"我懂"变成"我能讲"的步骤,
   而面试评的是后者。
