# 低延迟工程计划(TRV 实习申请专用,2026-08)

> 定位一句话:**不是把闪卡 App 伪装成 HFT,是在真实系统上演示"性能工程的方法"**:
> 定预算 → 测量 → 找到热路径上的浪费 → 优化 → 用百分位数字说话。
> 方法是可迁移的,数字是真实的,边界是诚实的(毫秒世界,不是微秒世界)。

## 三层策略

**第一层:重述已有工作(零代码,立刻可用)。** 系统里已有大量"延迟动机"的设计,
只是从没用延迟语言讲过:
- 6-CTE 单语句摄入 = **写路径消除往返**(1 次 RTT 而不是 4 次);
- keyset 分页 = 翻页 O(1),OFFSET 是 O(n) 扫描,**尾延迟随深度爆炸**;
- delta patch 327 字节 = **移动网络上的尾延迟/带宽优化**;
- MaxPoolSize=1 + 连接复用 + SnapStart hooks = **热路径上没有握手**;
- 队列单写者 promise 链 = **无锁竞争的临界路径**;
- 501 张卡/块 sha256 分块 = 坏块重传粒度 = 长尾控制。

**第二层:新增测量与优化(本计划的实现部分,要产出真数字)。**

**第三层:独立 LOB 作品**(见 13-lob-project-mapping.md 的四步计划,不在本仓库)。

## 实现范围(两个 agent)

### A · 移动端:热路径基准 + 一个真实优化(前后数字)

1. **纯核心基准**(新脚本 `mobile/scripts/bench-hot-paths.ts`,node 可跑):
   - `scheduleNextReview`:ops/sec(单次评分的调度计算);
   - `selectDrawCards`:200 张池单抽/十连 ops/sec;
   - `foldProgress`:1000 条事件重放耗时。
   输出表格(中位数,预热后测,注明 V8/机器)。
2. **发现并修复一个真实热路径浪费**(这是叙事核心):
   评分热路径上的 `enqueueProgressEvent` 每次都 `readQueue()`:
   **把整个队列 JSON.parse 一遍,push 一条,再整队列 JSON.stringify 写回**。
   队列深度 3000 时,每次点击都是 O(n) 的解析+序列化。
   优化:**写通缓存(write-through cache)**——内存里保存已解析的队列数组
   (已有 promise 链单写者保护,天然一致),enqueue 变 O(1) 追加 + 一次序列化写盘;
   读盘只在冷启动发生一次。
   **必须产出前后对比**:深度 0/1000/3000 下单次 enqueue 的耗时,优化前 vs 优化后。
   全部既有测试(408)必须仍绿——正确性不变量优先于任何优化。
3. 诚实记录 durability-vs-latency 取舍:事件先落盘是刻意的
   (事实先于投影),优化只消除重复解析,**不把落盘挪出热路径**——
   这个取舍本身就是面试素材(交易系统里同款问题叫 fsync 策略)。

### B · 服务端:摄入延迟测量(生产真数字)

1. `ProgressEvents.cs` 加最小计时(Stopwatch:解析/SQL/总耗时,一行结构化日志)。
   部署到生产(沿用既有 zip+update-function-code 流程)。
2. **生产测量脚本**(scratchpad,复用 smoke 测试的合成事件机制,
   sub=perf-test-20260816):
   - 预热后连续 invoke 200 次(批大小 1 与 25 各 100 次),记录端到端延迟;
   - 冷启动测量:改环境变量强制新容器,测 5 次冷启动(SnapStart 生效下的数字);
   - 产出:p50/p95/p99 表(warm,按批大小)+ 冷启动均值,写明测量方法。
3. 不做的事(诚实边界):不上 AOT、不改架构、不追微秒——
   Lambda+托管 Postgres 的物理下限就是个位数毫秒,写清楚这个下限是什么构成的
   (网络跳数),**知道下限在哪比数字本身更显功力**。

## 结果

### A1 · 纯核心热路径(M3 Max, Node v24.9, 15 轮取中位)

| workload | 中位 | p95 | 吞吐 |
|---|---:|---:|---:|
| scheduleNextReview(一次评分) | 23.7 ns | 42.2 ns | 42.2 M/s |
| selectDrawCards(200 张池,单抽) | 8.48 µs | 8.63 µs | 118 k/s |
| selectDrawCards(200 张池,十连) | 11.19 µs | 11.48 µs | 89 k/s |
| foldProgress(重放 1000 事件) | 152.3 µs | 158.2 µs | 6.6 k/s |

读法:业务计算本身不是瓶颈。一次评分的调度计算是**纳秒级**,
所以评分路径上的成本全部来自存储序列化,不是算法。

### A2 · 写通缓存:优化前后(recordReviewEvent 单次入队)

| 队列深度 | 优化前 中位 | 优化后 中位 | 提升 |
|---:|---:|---:|---:|
| ~0 | 24.4 µs | 157.9 µs | (见下方说明) |
| ~1000 | 1.617 ms | 0.887 ms | **1.8×** |
| ~3000 | 4.864 ms | 1.616 ms | **3.0×** |

两点拟合出的深度斜率(每条已排队事件的边际成本):

- 优化前:**1.62 µs × depth**(每次入队都 parse 整个队列 + 再 stringify 整个队列)
- 优化后:**364.5 ns × depth**(内存里已有解析结果,只剩一次 stringify)
- **斜率降到 22.5%**,即消掉了约 78% 的深度相关浪费(parse 那一半)。

深度 0 那行变慢是真实的、也是可接受的:缓存版把 token 读取等固定开销挪进了
计时窗口内(冷启动首次入队 370 µs vs 212 µs)。**在队列空的时候我们本来就不慢,
优化针对的是深度大时的尾部**:深度 3000 是离线一周的用户,那里 4.9 ms → 1.6 ms。

**没有动的东西(这是取舍不是遗漏)**:事件仍然是先序列化落盘再返回。
`stringify` 留在热路径上是因为持久化本身就是这一步的目的
(事实先于投影)。缓存只消除重复解析,不把落盘挪出热路径。
真要再快,方案是追加写(append-only)而不是每次重写整个数组,
代价是需要压缩(compaction),那是另一个正确性评审。

### B · 生产服务端摄入延迟(core-vpc, 128 MB, ap-southeast-2)

测量方式:本机 → `lambda:Invoke`,合成事件,全新 UUID(真插入,不走幂等快路径),
预热 30 次,**打乱顺序交错跑** 200 次(分块跑会让先跑的批次替后者付 JIT 的账,
第一轮就踩到过,反例样本保留在 perf/results/warm_samples_blocked.json)。

| 批大小 | e2e p50 | e2e p95 | e2e p99 | server p50 | handler p50 |
|---:|---:|---:|---:|---:|---:|
| 1 | 102.8 ms | 139.5 ms | 152.3 ms | 58.9 ms | 37.1 ms |
| 25 | 118.9 ms | 140.4 ms | 159.4 ms | 74.1 ms | 53.3 ms |

**每事件成本:batch=1 是 36.9 ms,batch=25 是 2.1 ms(1/17)。** 批处理的价值在这。

handler 内部拆解(中位):

| 分段 | batch=1 | batch=25 | 读法 |
|---|---:|---:|---|
| 连接获取 | 0.007 ms | 0.007 ms | MaxPoolSize=1 复用生效,热路径无握手 |
| 解析+校验 | 0.052 ms | 0.160 ms | **每事件约 6 µs,占 0.14-0.30%,根本不是热点** |
| 6-CTE 单语句 | 19.9 ms | 19.9 ms | 批大小 ×25,这条语句几乎不变贵 |
| 事务壳(BEGIN + users upsert + COMMIT) | **30.6 ms** | **32.6 ms** | **比正事还贵**,三次额外往返 |

冷启动(n=5,**SnapStart 实际是关闭的**,与计划书假设不符,如实记录):

| 指标 | 均值 |
|---|---:|
| e2e | 9228 ms |
| Lambda init | 303 ms |
| 首次建库连接 | **4294 ms(占 handler 的 68%)** |

### 下限在哪(比数字本身更值得讲)

端到端 ~100 ms 的构成:公网往返 45-50 ms(改不掉)+ Lambda 派发 ~21 ms +
handler 37-53 ms。而 handler 里业务计算只占 0.05-0.16 ms,**其余几乎全是到
Postgres 的 4 次网络往返**(BEGIN / users upsert / 6-CTE / COMMIT)。

所以这套架构热路径的下限 ≈ 4 × VPC 内 RTT + 一次公网 RTT。
**要再降只能减往返数或减跳数,不是优化代码。** 这是毫秒世界,不是微秒世界。

下一个可回收的浪费已经定位:把 users upsert 并进主语句(第七个 CTE)
或去掉显式事务(单语句本身已原子),可省约 31 ms / 3 次往返——
但它动写序与事务边界,属于正确性不变量,必须单独配 Testcontainers 评审。
